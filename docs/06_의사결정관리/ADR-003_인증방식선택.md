# ADR-003. 인증 방식 선택

## 상태

승인됨

## 배경

초기에는 본인인증을 통해 사용자를 유니크하게 식별하는 방안을 검토했다. 그러나 휴대폰 본인확인과 실명확인은 비용 부담이 있어 MVP 범위에서 제외한다.

대신 카카오, 네이버, 구글 간편로그인은 구현 가능성이 높고 사용자 접근성이 좋으므로 신규 프로젝트의 인증 수단으로 채택한다.

## 결정

1. PDFrend의 내부 회원은 `user_id`로 관리한다.
2. 본인인증은 MVP 범위에서 제외한다.
3. 카카오, 네이버, 구글 간편로그인을 제공한다.
4. 이메일, 이름, 전화번호 동일성으로 계정을 자동 통합하지 않는다.
5. 간편로그인 제공자의 고유 식별자 `(provider, provider_user_id)`를 로그인 수단의 유니크 키로 사용한다.
6. 로그인한 상태에서 추가 간편로그인을 등록할 수 있다.
7. 연결하려는 벤더 ID가 이미 다른 내부 계정에 연결되어 있으면 자동 병합하지 않고 사용자 동의 기반 계정 통합 절차를 제공한다.

## 계정 통합 결정

예시 흐름:

```text
1. A01 ID 계정 등록
2. A02 카카오 계정 등록(kakao01)
3. A01 ID 계정 로그인 + 카카오 간편로그인 등록(kakao01)
4. 시스템이 kakao01이 A02에 연결되어 있음을 확인
5. 사용자에게 A01/A02 계정 통합을 안내
6. 사용자 동의 후 대표 계정 기준으로 통합
```

이 결정은 법적 동일인 인증이 아니다. 두 내부 계정 모두에 접근 가능한 사용자가 동일 벤더 계정 인증을 성공했다는 사실을 근거로 서비스 계정 통합을 허용하는 정책이다.

## 결과

### 긍정적 영향

- 본인인증 비용 없이 로그인 편의성을 확보한다.
- 여러 소셜 계정을 하나의 내부 회원에 연결할 수 있다.
- 이메일 동일성에 의존하지 않아 계정 탈취와 오통합 위험을 줄인다.
- 중복 가입된 계정을 사용자가 직접 통합할 수 있다.

### 부정적 영향

- 법적 동일인 보장은 제공하지 않는다.
- 계정 통합 UX와 데이터 이전 로직이 필요하다.
- 카카오, 네이버, 구글 개발자 앱과 시크릿 관리가 필요하다.

## 후속 작업

- 하네스 기반 인증 구현 방식 검토
- OAuth 제공자별 Redirect URI 등록
- 계정 통합 화면 정의
- AuthIdentity 테이블 설계
- 통합 감사 로그 설계
