# 하네스 작업 운영 절차

## 1. 목적

세션 관리, 태스크 처리, 루프 기반 반복 개선처럼 반복되는 프로젝트 운영 작업을 하네스 작업으로 등록하고, 실행 순서, 파일 수정 권한, 산출물을 추적 가능하게 관리한다. 또한 **모든 에이전트 작업은 PostgreSQL 작업정보 DB(`harness_*`, `agent_*`)와 실시간으로 동기화되어 엄격한 무결성을 유지**해야 한다.

## 2. 하네스 3계층 작업 목록 및 파일 수정 권한 (⭐️ 핵심 규칙)

> [!IMPORTANT]
> **문서, 코드, 소스 수정 작업은 오직 `태스크처리`, `세션정리`, `루프처리` 단계에서만 가능하다.**<br>
> 그 외의 모든 단계는 Read-Only / 계획 수립 / 검증 / 상태 확인만 수행하며, 파일 수정을 엄격히 금지한다.<br>
> **모든 단계의 진입 및 완료는 작업정보 DB와 100% 실시간 영속화(Real-time DB Sync)되어야 한다.**

## 3. 세션 계층 운영 절차

### 3.1 #세션시작
1. 이전 세션의 인계사항과 미완료 이슈를 확인한다.
2. 현재 git 브랜치와 워킹트리 상태를 점검한다.
3. 이번 세션의 목표와 태스크 계획을 수립하고 에이전트 서비스 세션 시작 API(`POST /api/agent/v1/sessions/start`)를 호출한다.
4. 응답 마지막에 `#태스크시작` 복사용 코드블록을 제시한다.

### 3.2 #세션정리
1. **세션명 정리**: 세션번호를 유지하고 세션 작업 내용을 반영해 `세션번호-작업내용` 형식으로 정리한다.
2. **세션 리뷰 및 회고 문서 작성**: 이번 작업 요약, 변경 문서, 검증 내용, 회고(KPT), 다음 작업 목표를 `docs/10_리뷰관리/YYYYMM/DD/`에 작성한다.
3. **백로그 대장 갱신**: 태스크 도중 발굴되어 세션 내 미착수된 임시 백로그(`DRAFT-XX`)에 공식 번호(`BL-YYYYMMDD-XXX`)를 채번하여 `docs/11_로그/백로그_대장.md` 및 DB에 등재한다.
4. **문서 크로스체크 검증**: 로컬 `/docs` 파일들과 DB 문서 간 정합성을 검증하는 크로스체크 API(`POST /api/agent/v1/docs/verify-consistency`)를 호출한다.
5. **세션 마무리 약식 PR 생성**: 세션 산출물(회고, 로그 등)을 `dev`에 반영하기 위한 약식 PR을 생성하고 세션 완료 API(`POST /api/agent/v1/sessions/complete`)를 호출한다.
6. **응답 코드블록 제시**: 다음 단계로 `#세션종료` 복사용 코드블록을 제시한다.

### 3.3 #세션종료
1. 다음 세션명(`세션번호-작업내용`)과 남은 작업 현황, 인계사항을 채팅으로 작성하여 전달한다.

## 4. 태스크 계층 운영 절차

### 4.1 #태스크시작
1. `main` 브랜치 기준 `task/한글-작업명_에이전트명` 작업 브랜치를 생성하고 전환한다.
2. 태스크의 요구사항과 수정 대상을 분석하고 실행 계획을 수립한 뒤 태스크 시작 API(`POST /api/agent/v1/tasks/start`)를 호출한다.
3. 응답 마지막에 `#태스크처리` 복사용 코드블록을 제시한다.

### 4.2 #태스크처리
1. 소스 코드, 단위 테스트, 설정 파일, 관련 문서를 실제로 작성/수정한다.
2. 작업 중 새로운 아이디어나 부가 과제가 발생하면 태스크 내 `draft_backlogs`에 임시 등록한다. (세션 내 즉시 착수 시 신규 태스크로 승격)
3. 복합 반복 작업이 필요한 경우 루프 계층(`#루프분석` -> `#루프기획` -> `#루프설계` -> `#루프처리` -> `#루프정리`)으로 진입한다.
4. 응답 마지막에 `#태스크정리` 복사용 코드블록을 제시한다.

### 4.3 #태스크정리
1. **루프 가드 (Loop Guard) 검증**: 태스크 내 모든 루프가 `정리(COMPLETED)` 또는 `정지(ABORTED)` 상태인지 확인한다.
2. `git diff --check`, `npm run typecheck`, `npm run test:unit`, `npm test`, `npm run build` 검증을 수행한다.
3. 변경 의도를 담은 한 줄 요약 커밋을 생성하고 `dev` 대상 PR을 등록한다.
4. 리뷰어(사람)의 PR 검토 및 `dev` 머지를 완료한다.
5. 변경된 마크다운 문서를 DB에 현행화하는 API(`POST /api/agent/v1/docs/sync`) 및 태스크 정리 API(`POST /api/agent/v1/tasks/clean`)를 호출한다.
6. 응답 마지막에 `#태스크승급` 복사용 코드블록을 제시한다.

### 4.4 #태스크승급
1. `dev -> stg`를 직접 머지한다 (별도 승급 PR 없음).
2. `stg -> main`을 직접 머지한다 (`main`은 서비스 운영 prd).
3. 승급 머지 메시지와 이슈 댓글에 이슈번호, 원천 PR번호, 승급 머지 SHA를 기록하고 태스크 승급 API(`POST /api/agent/v1/tasks/promote`)를 호출한다.
4. 완료된 GitHub 이슈를 종료한다.
5. 응답 마지막에 `#세션정리` 복사용 코드블록을 제시한다.

## 5. 루프 계층 운영 절차

태스크 내부에서 반복적이고 정밀한 TDD, 단위 리팩터링, 컴포넌트 구현이 필요할 때 실행한다.

### 5.1 #루프분석 / #루프기획 / #루프설계 (Read-Only)
- 루프 작업 적합성을 검토하고 WorkItem 목표, 허용 경로(`allowedPaths`), 완료 조건, 검증 명령을 정의한다.
- 체크포인트 롤백 기준과 테스트 시나리오를 설계한다.

### 5.2 #루프처리 (Write 허용)
- before 체크포인트를 생성하고 허용 경로 내에서 소스 코드 및 테스트 코드를 작성/수정한다.

### 5.3 #루프정리 (Read-Only)
- 단위 검증 명령을 실행하여 성공 시 after 체크포인트와 diff 요약을 기록하고 부모 태스크로 결과를 통합한다.
- 문서 수정이 발생한 경우 `POST /api/agent/v1/docs/sync`를 호출한다.

### 5.4 #루프제어 (정지/보류/보완)
- **#루프보완 (`REVISE`)**: 테스트 실패 시 설계를 보완하고 `#루프처리`로 재진입한다.
- **#루프보류 (`HOLD`)**: 외부 의존성 등으로 일시 정지한다.
- **#루프정지 (`ABORT`)**: 작업 취소 시 체크포인트로 롤백하고 루프를 종결한다.
