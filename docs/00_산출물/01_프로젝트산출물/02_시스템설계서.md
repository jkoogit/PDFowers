# 시스템 설계서

## 1. 목적

PDFowers의 요구사항을 구현 가능한 시스템 구성요소, 책임, 데이터 흐름, 오류 처리 기준으로 정리한다. 본 문서는 상세 DB 설계서, API 명세서, UI/UX 문서 작성 전 기준 설계서로 사용한다.

## 2. 설계 범위

| 포함 | 제외 또는 후속 문서 |
| :--- | :--- |
| 핵심 도메인, 인증/계정 통합 흐름, PDF 처리 흐름, 감사/보안 기준 | 상세 ERD, 엔드포인트별 API 스펙, 화면 와이어프레임, 운영 절차 |

## 5. 인증 및 계정 통합 설계

### 5.1 내부 식별자

- 내부 회원의 기준 식별자는 `User.id`다.
- 외부 로그인 계정은 회원 본체가 아니라 `AuthIdentity`로 관리한다.
- `(provider, provider_user_id)`는 전역 유니크 제약을 가진다.

### 5.2 로그인 흐름

```text
OAuth/OIDC 인증 완료
  -> 제공자 사용자 정보 조회
  -> (provider, provider_user_id) 조회
  -> 기존 AuthIdentity 있음: 연결된 User로 로그인
  -> 기존 AuthIdentity 없음: ID/PW와 인증 이메일 입력 후 신규 User 및 AuthIdentity 생성
  -> 인증 이메일은 작업 알림 발송 대상으로 등록
```

ID/이메일 로그인은 내부 계정 자격 증명과 인증 이메일을 기준으로 처리한다. 이메일은 로그인 수단과 작업 알림 수신 대상이지만, 계정 자동 통합의 단독 근거로 사용하지 않는다.

### 5.3 로그인 수단 연결 흐름

```text
로그인 사용자 A01
  -> 간편로그인 연결 요청
  -> OAuth/OIDC 인증 완료
  -> 연결 이력 없음: A01에 AuthIdentity 연결
  -> A01에 이미 연결됨: AUTH_IDENTITY_ALREADY_LINKED
  -> 다른 사용자 A02에 연결됨: ACCOUNT_MERGE_REQUIRED
```

### 5.4 계정 통합 흐름

```text
ACCOUNT_MERGE_REQUIRED
  -> 통합 안내 화면 표시
  -> 두 계정의 주요 데이터 범위 안내
  -> 사용자 명시적 동의
  -> 대표 계정 결정
  -> 서버 트랜잭션 시작
  -> AuthIdentity, Document, Annotation, Sharing, Settings 이전
  -> 보조 User를 merged 상태로 변경
  -> AuditLog 기록
  -> 트랜잭션 커밋
```

## 6. 문서 처리 설계

### 6.1 업로드

```text
사용자 PDF 업로드
  -> 권한 및 용량 확인
  -> 원본 PDF 저장
  -> Document 메타데이터 생성
  -> PDF 처리 작업 등록
  -> 페이지 이미지/OCR/목차 후보 생성
  -> 처리 결과 상태 갱신
```

### 6.2 편집 데이터 분리

- 원본 PDF는 보존한다.
- 주석, 목차, 북마크, OCR 텍스트, 버전 정보는 별도 데이터로 관리한다.
- 다운로드 시 원본 PDF와 편집 데이터를 결합하여 표준 PDF를 생성한다.
- 다운로드 파일명은 `[도서명]_[버전]_[수정일자]_[수정시간].pdf` 형식을 기본 후보로 한다.
- 다운로드 후 재업로드된 PDF는 기존 문서/버전 후보와 매칭할 수 있어야 한다.
- 매칭 실패 또는 충돌 시 사용자가 대상 문서와 버전을 직접 선택하도록 한다.

### 6.3 버전 관리

- 주요 변경 시 체크포인트를 생성한다.
- 버전별 변경 이력은 사용자, 변경 일시, 변경 요약을 포함해야 한다.
- 상세 복원 정책은 후속 버전 설계에서 확정한다.

### 6.4 주석 영역 편집

- 주석 영역 편집은 OCR 편집이 아니라 Annotation 도메인의 책임으로 둔다.
- 주석 대상 영역의 이미지 캡처, 붙여넣기, 텍스트 수정, 검색을 지원 후보로 둔다.
- Xodo 호환 Annotation 타입과 내부 주석 모델의 변환 기준은 테스트 계획서에서 검증한다.

## 7. 공유 및 권한 설계

- 문서 소유자는 공유 대상을 지정할 수 있다.
- 공유 권한은 읽기, 주석 작성, 본인 주석 수정, 전체 주석 수정, 댓글 작성/수정 등 역할 기반으로 확장 가능하게 설계한다.
- 공유 만료 조건을 둘 수 있어야 한다.
- 공유받은 문서는 수신자의 업로드 용량에 포함하지 않는다.
- 계정 통합 시 공유 권한은 대표 계정 기준으로 재연결한다.
- 공개 읽기 링크는 후보 기능으로 두며, 허용 범위와 보안 정책이 결정되기 전까지 기본 기능으로 확정하지 않는다.
- 공유 권한 변경은 가능한 한 뷰어 접근과 편집 가능 상태에 즉시 반영한다.

## 8. 동기화 설계

- 여러 기기에서 문서 작업 상태를 이어갈 수 있어야 한다.
- 오프라인 변경은 변경 묶음 단위로 기록하는 방식을 후보로 둔다.
- 충돌 해결 정책은 후속 상세 설계에서 확정한다.

## 8.1 비동기 작업 큐 설계

- PDF 분리/병합, 작업 알림, 동기화 이벤트는 비동기 작업 큐 적용 대상으로 둔다.
- 작업 큐가 필요한 경우 Job Queue Adapter를 통해 특정 제품 의존성을 격리한다.
- RabbitMQ는 후보 제품으로 등록하되, 채택 여부는 별도 아키텍처 결정으로 확정한다.

## 9. 스토리지 설계

| ID | 저장 대상 | 설명 |
| :--- | :--- | :--- |
| `000209_001` | 원본 PDF | 사용자가 업로드한 원본 |
| `000209_002` | 페이지 이미지 | 뷰어와 OCR 처리를 위한 이미지 |
| `000209_003` | OCR 텍스트 | 검색 및 AI 검색 키워드 후보에 활용 |
| `000209_004` | 병합 PDF | 다운로드 또는 내보내기 결과물 |

스토리지 구현은 NAS 스토리지와 원격지 Ubuntu 스토리지를 모두 검토 대상으로 둔다. 최종 운영 조합은 테스트 운영 후 ADR로 확정한다.

## 10. 보안 설계

- OAuth Client Secret, DB 비밀번호, 세션 키는 환경변수 또는 시크릿 저장소로 관리한다.
- 문서와 로그에는 실제 시크릿 값을 기록하지 않는다.
- OAuth `state` 값을 사용하여 CSRF를 방지한다.
- Redirect URI는 제공자 콘솔 등록 값과 정확히 일치해야 한다.
- 토큰, Client Secret, Authorization Code는 애플리케이션 로그에 남기지 않는다.

## 11. 오류 상태

| ID | 코드 | 의미 | 처리 |
| :--- | :--- | :--- | :--- |
| `000211_001` | `AUTH_IDENTITY_ALREADY_LINKED` | 로그인 수단이 이미 현재 계정에 연결됨 | 사용자에게 이미 연결됨 안내 |
| `000211_002` | `ACCOUNT_MERGE_REQUIRED` | 로그인 수단이 다른 내부 계정에 연결됨 | 계정 통합 안내로 전환 |
| `000211_003` | `LAST_AUTH_IDENTITY_REQUIRED` | 마지막 로그인 수단 해제 불가 | 해제 차단 및 이유 안내 |
| `000211_004` | `ACCOUNT_MERGE_CONFLICT` | 병합 대상 데이터 충돌 | 통합 중단 또는 사용자 선택 요청 |

## 12. 검토 필요사항

- DB 상세 스키마와 인덱스
- API 경계와 인증 세션 방식
- PDF 처리 작업 큐 방식
- RabbitMQ 채택 여부
- 공개 링크 보안 범위
- 스토리지 어댑터 구현 방식
- 동기화 충돌 해결 정책
- Cloudtype/NAS Docker 운영 분담
