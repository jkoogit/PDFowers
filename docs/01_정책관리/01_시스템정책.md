# 01. 시스템 정책

## 목적

PDFowers 신규 프로젝트의 서비스 운영, 인증, 계정, 데이터 관리 기준을 정의한다. 본 문서는 하네스 기반 구현 전 정책 기준이며, 세부 구현은 설계/기술 문서와 ADR에서 보완한다.

## 1. 회원 및 인증 정책

### Policy-AUTH-001: 내부 회원 식별자

- 회원의 최종 식별자는 외부 로그인 계정이나 사용자가 입력한 로그인 ID가 아니라 서비스 내부 `user_srno`다.
- `user_srno`는 사용자가 알 수 없는 시스템 시리얼 번호이며, UUID 사용을 기본 후보로 한다.
- 사용자가 입력하는 로그인 ID는 `login_id`로 별도 관리한다.
- 카카오, 네이버, 구글 계정은 회원을 식별하는 본체가 아니라 로그인 수단이다.

### Policy-AUTH-002: 본인인증 제외

- 휴대폰 본인확인, 실명확인, 주민등록 기반 본인인증은 비용 문제로 MVP 범위에서 제외한다.
- 간편로그인은 법적 동일인 인증으로 사용하지 않는다.
- 서비스는 간편로그인을 통해 "해당 외부 계정에 접근 가능한 사용자"만 확인한다.

### Policy-AUTH-003: 간편로그인 제공자

- MVP 후보 간편로그인 제공자는 카카오, 네이버, 구글이다.
- 각 제공자는 OAuth 또는 OIDC 기반으로 연동한다.
- 제공자별 사용자 고유 식별자는 `(provider, provider_user_id)`로 관리한다.
- 간편로그인 기반 회원가입 시에도 서비스 로그인용 ID와 비밀번호를 필수 입력한다.

### Policy-AUTH-004: 이메일 자동 통합 금지

- 이메일, 이름, 전화번호가 같다는 이유만으로 내부 계정을 자동 통합하지 않는다.
- 외부 제공자가 반환하는 이메일은 미제공, 변경, 비공개, 재사용 가능성이 있으므로 계정 통합의 단독 근거로 사용하지 않는다.
- 이메일은 회원가입, 로그인, 사용자 안내, 알림 발송에 사용할 수 있는 계정 식별 근거다.
- 다만 이메일 동일성만으로 내부 계정을 자동 통합하지 않는다.
- 인증 이메일은 작업 알림 발송 대상이며, 알림 발송 전 수신 동의를 확인한다.

### Policy-AUTH-005: 간편로그인 연결

- 사용자가 로그인한 상태에서 추가 간편로그인을 등록할 수 있다.
- 연결하려는 `(provider, provider_user_id)`가 어떤 내부 계정에도 연결되어 있지 않으면 현재 로그인한 `user_srno`에 연결한다.
- 연결하려는 `(provider, provider_user_id)`가 다른 내부 계정에 이미 연결되어 있으면 자동 연결하지 않고 대상 계정에 병합 요청을 보낸다.
- 계정 통합은 대상 계정으로 로그인한 사용자가 요청을 수용한 뒤 진행한다.

### Policy-AUTH-006: 계정 통합

- 계정 통합은 사용자의 명시적 동의가 있을 때만 수행한다.
- 동일한 벤더 계정에 대한 OAuth 인증을 성공한 경우, 두 내부 계정에 대한 접근권이 확인된 것으로 보고 통합 후보로 제시할 수 있다.
- 통합 시 대표 계정을 선택하고, 문서, 주석, 공유 권한, 설정, 감사 로그의 이전 범위를 명확히 안내한다.
- 병합되는 계정은 즉시 물리 삭제하지 않고 `merged` 상태와 `merged_into_user_srno`를 남긴다.
- 대상 계정 사용자는 통합되는 정보 범위와 동의 여부를 확인한 뒤 통합을 승인해야 한다.

### Policy-AUTH-007: 마지막 로그인 수단 보호

- 사용자는 여러 로그인 수단을 연결할 수 있다.
- 마지막 남은 로그인 수단은 해제할 수 없다.
- 로그인 수단 연결, 해제, 통합은 감사 로그에 기록한다.

### Policy-AUTH-008: ID/이메일 로그인

- 서비스 로그인 방식은 ID, 이메일, 간편로그인을 지원 대상으로 둔다.
- 이메일 회원가입 시 서비스 로그인용 ID와 비밀번호를 필수 입력한다.
- 이메일 인증은 회원가입/로그인 인증 수단이자 작업 알림 발송 대상 이메일을 확인하기 위한 절차로 사용한다.
- 이메일 인증 필수 여부는 시스템 설정으로 관리할 수 있다.
- 이메일 인증이 필수가 아닌 경우 ID 로그인은 이메일 인증 없이 처리할 수 있으며, 회원가입 시 이메일 인증 옵션과 알림 제공 안내를 표시한다.
- 이메일 인증이 필수인 경우 회원가입 시 이메일 인증을 필수로 요구하고, ID 로그인은 이메일 인증 완료 후 처리한다.
- 간편로그인은 이메일 인증 시스템 설정과 관계없이 외부 제공자 인증을 기준으로 로그인 처리한다.
- 2차 인증은 현재 MVP 필수 범위에 포함하지 않는다.

## 2. 민감정보 관리 정책

### Policy-SEC-001: 비밀값 저장 금지

- 계정 비밀번호, OAuth Client Secret, DB 비밀번호, 인증키, 계좌 정보, 개인정보 원문은 Git, 문서, 이슈, 리뷰, 대화 기록에 저장하지 않는다.
- 문서에는 환경변수명, 용도, 필수 여부, 민감정보 여부만 기록한다.
- 예시 값은 실제 값처럼 보이지 않는 더미 값만 사용한다.

### Policy-SEC-002: 환경별 시크릿 분리

- 로컬, 테스트, 운영 환경의 OAuth 앱과 DB 계정은 분리한다.
- 로컬은 `.env.local`, 배포 환경은 Cloudtype 환경변수/시크릿, CI/CD는 GitHub Secrets 사용을 기본 후보로 한다.
- 운영 시크릿은 최소 권한 계정으로 발급하고, 노출 의심 시 즉시 회전한다.

## 3. 스토리지 및 용량 정책

- 신규 가입 사용자 기본 업로드 용량은 정책으로 관리한다.
- 공유받은 문서는 수신자의 업로드 용량에 포함하지 않는다.
- NAS는 이미지 저장소, 원격지 Ubuntu는 PDF 문서 저장소로 사용한다.
- Cloudtype은 배포 서비스로 사용하며 저장소로 사용하지 않는다.

## 4. AI 검색 정책

- AI 검색은 본인인증이나 계정 식별 기능이 아니다.
- AI 검색은 포털 검색처럼 사용자가 선택한 키워드를 외부 서비스로 전달하여 검색/질의하는 연동 기능으로 정의한다.
- 외부 서비스 연동 시 문서 원문, 개인정보, 민감정보가 불필요하게 전송되지 않도록 별도 정책을 둔다.

## 5. 공유 링크 정책

- 공유 링크는 대상 문서/버전, 권한, 만료 조건, 생성자, 접근 이력을 관리해야 한다.
- 로그인 사용자에게 부여되는 작업 권한과 비로그인 공개 읽기 권한은 분리한다.
- 공개 읽기 링크는 구현 대상이다.
- 공개 링크는 최소한 만료, 접근 로그, 권한 범위, 공유 중단 절차를 정의해야 한다.
- 공개 읽기 링크를 기본 서비스 화면 권한으로 제공할지, 별도 공개 읽기 화면으로 제공할지는 설계 단계에서 결정한다.

## 6. 작업 알림 정책

- 작업 알림은 인증되고 수신 동의한 이메일을 기본 발송 대상으로 한다.
- 알림 대상 이벤트 후보는 문서 공유, 공유 권한 변경, PDF 처리 완료/실패, 협업 변경, 계정 보안 이벤트다.
- 알림 발송 큐 또는 비동기 처리 방식은 시스템 설계 및 ADR에서 확정한다.
- 카카오 알림톡은 후속 알림 채널 후보이며, 비용 발생 여부를 확인한 뒤 적용 범위를 결정한다.
