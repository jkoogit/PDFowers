# 03. 설계관리

## 목적

시스템 구조, 도메인 경계, 데이터 모델, 환경 구성, 배포 구조를 관리한다.

## 기존 참고 문서에서 유지할 핵심

기존 설계는 도메인 중심 구조를 지향한다. 주요 도메인 후보는 다음과 같다.

| 도메인 | 책임 |
| :--- | :--- |
| User | 회원, 프로필, 인증수단, 권한, 저장소 할당량 |
| Document | 문서 생명주기, 메타데이터, 상태 |
| Version | 버전 생성, 체크포인트, 변경 추적 |
| Annotation | 주석 CRUD, 작성자, 검색, 상태 |
| Sharing | 공유 대상, 권한, 만료 |
| Sync | 실시간 동기화, 오프라인 변경, 충돌 해결 |
| Storage | 원본 PDF, 페이지 이미지, OCR, 병합 파일 저장 |
| Audit | 작업 로그, 인증 이벤트, 변경 이력 |

설계 원칙은 다음을 유지한다.

- 비즈니스 로직은 도메인 계층에 둔다.
- 외부 저장소, DB, 인증 제공자는 인프라 계층으로 격리한다.
- 도메인 이벤트로 감사 로그, 저장소 사용량, 알림 같은 부수 효과를 분리한다.
- 데이터 사전, 테이블 문서, 실제 스키마는 함께 현행화한다.

## 초기화 기준

기존 설계의 코드 예시와 폴더 구조는 참고만 한다. 하네스가 제공하는 기본 구조와 충돌하면 하네스 구조를 우선 검토한다.

## 검토 필요사항

- 도메인 모델의 회원 ID 타입은 UUID를 기본 후보로 두고 데이터 설계에서 확정한다.
- 기존 `S3/NAS 저장소` 표현은 실제 하네스 환경의 저장소 결정 후 확정해야 한다.
- `Notification Domain`은 아키텍처 개요에 등장하지만 도메인 목록에는 없다. 실제 범위에 포함할지 결정해야 한다.
- 문서 메타데이터를 PDF 내부에 기록하는 방식과 DB 기준 메타데이터의 우선순위를 결정해야 한다.
