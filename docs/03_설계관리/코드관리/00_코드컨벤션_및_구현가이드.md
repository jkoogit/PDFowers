# 00. 코드 컨벤션 및 구현 가이드 (for Developer)

## 1. 개요 및 학습 목표

본 가이드는 PDFowers 프로젝트에 참여하는 모든 개발자가 **읽기 쉽고(Readable), 수정하기 안전하며(Maintainable), 스스로 검증 가능한(Testable) 고품질 코드**를 작성할 수 있도록 돕는 실무 지침서다.

초급 개발자도 쉽게 이해할 수 있도록 **객체지향 프로그래밍(OOP)과 도메인 주도 설계(DDD)의 핵심 개념, 디자인 패턴 실무 적용법, 친절한 주석 작성법**을 풍부한 예시와 함께 설명한다.

## 2. 객체지향(OOP)과 도메인 주도 설계(DDD) 핵심 원칙

### 2.1 빈약한 도메인 모델(Anemic Domain Model) vs 풍부한 도메인 모델(Rich Domain Model)

> 💡 **핵심 요약**: 데이터만 담고 있는 수동적인 객체(Getter/Setter만 있는 DTO) 대신, **자신의 비즈니스 규칙을 스스로 검증하고 행동(메서드)하는 객체**를 만들어야 한다.

#### ❌ 나쁜 예 (빈약한 모델 - 서비스 계층에 비즈니스 로직이 파편화됨)
```typescript
// Task 객체는 단순 데이터 주머니일 뿐
class Task {
  public id: string;
  public status: string;
  public activeLoops: Loop[] = [];
}

// 서비스에서 일일이 검증하고 상태를 변경함 (버그 유발 가능성 높음)
class TaskService {
  completeTask(task: Task) {
    // 비즈니스 규칙: 활성 루프가 있으면 정리가 불가능하다!
    for (const loop of task.activeLoops) {
      if (loop.status !== '정리' && loop.status !== '정지') {
        throw new Error('미완료 루프가 존재합니다.');
      }
    }
    task.status = '정리'; // 외부에서 상태를 마음대로 변경 (캡슐화 파괴)
  }
}
```

#### ⭕ 좋은 예 (풍부한 도메인 모델 - 엔티티가 스스로 비즈니스 규칙을 강제함)
```typescript
/**
 * 태스크(Task) 도메인 엔티티
 * - 상태 전이와 루프 가드(Loop Guard) 규칙을 스스로 보호한다.
 */
export class TaskEntity {
  private _status: TaskStatus;
  private readonly _loops: Map<string, LoopEntity> = new Map();

  constructor(
    public readonly id: string,
    public readonly sessionId: string,
    public readonly name: string,
    initialStatus: TaskStatus = '시작'
  ) {
    this._status = initialStatus;
  }

  get status(): TaskStatus {
    return this._status;
  }

  /**
   * 태스크 정리(Clean) 비즈니스 메서드
   * @throws {LoopGuardViolationException} 미완료 루프가 남아있을 경우 예외 발생
   */
  public clean(summary: string): void {
    // 1. 도메인 규칙 검증 (Loop Guard)
    const activeLoops = Array.from(this._loops.values()).filter(
      (loop) => !loop.isTerminalState()
    );

    if (activeLoops.length > 0) {
      throw new LoopGuardViolationException(
        `태스크를 정리할 수 없습니다. 미완료 루프가 ${activeLoops.length}개 남아있습니다.`
      );
    }

    // 2. 상태 전이
    this._status = '정리';
  }
}
```

### 2.2 엔티티(Entity) vs 값 객체(Value Object, VO)

| 구분 | 엔티티 (Entity) | 값 객체 (Value Object) |
| :--- | :--- | :--- |
| **식별자** | 고유 식별자(`id`, `uuid`)를 가짐 | 식별자 없음 (모든 속성 값이 같으면 같은 객체) |
| **가변성** | 생명주기에 따라 상태가 변함 (가변) | 한 번 생성되면 절대 변하지 않음 (**불변, Immutable**) |
| **비교 방식** | `taskA.id === taskB.id` (ID로 비교) | `tokenUsageA.equals(tokenUsageB)` (값으로 비교) |
| **예시** | `SessionEntity`, `TaskEntity`, `UserAccount` | `TokenUsageVO`, `AuditMetaVO`, `WorkItemVO` |

#### 값 객체(VO) 작성 예시: `TokenUsage`
```typescript
/**
 * 토큰 소비량 값 객체 (불변)
 */
export class TokenUsage {
  constructor(
    public readonly promptTokens: number,
    public readonly completionTokens: number
  ) {
    if (promptTokens < 0 || completionTokens < 0) {
      throw new Error('토큰 수는 음수일 수 없습니다.');
    }
  }

  get totalTokens(): number {
    return this.promptTokens + this.completionTokens;
  }

  /** 새로운 토큰을 더할 때 기존 객체를 수정하지 않고 새 객체를 반환 (불변성 유지) */
  public add(other: TokenUsage): TokenUsage {
    return new TokenUsage(
      this.promptTokens + other.promptTokens,
      this.completionTokens + other.completionTokens
    );
  }
}
```

## 3. 실무 디자인 패턴 적용 가이드

### 3.1 상태 패턴 (State Pattern) & 상태 전이 머신
- 하네스의 복잡한 상태(`시작` ➔ `분석` ➔ `처리` ➔ `정리` ➔ `승급`)를 수많은 `if/else` 대신 **명시적인 상태 전이 매트릭스**로 관리한다.

```typescript
export const TASK_TRANSITIONS: Record<TaskStatus, TaskStatus[]> = {
  시작: ['분석', '처리', '보류', '폐기'],
  분석: ['처리', '보류', '폐기'],
  처리: ['정리', '보류', '폐기'],
  정리: ['승급', '보류', '폐기'],
  승급: ['완료', '보류', '폐기'],
  완료: [],
  보류: ['시작', '분석', '처리', '정리'],
  폐기: []
};

export function validateTaskTransition(from: TaskStatus, to: TaskStatus): void {
  const allowed = TASK_TRANSITIONS[from];
  if (!allowed.includes(to)) {
    throw new InvalidStateTransitionException(
      `태스크 상태를 [${from}]에서 [${to}](으)로 변경할 수 없습니다.`
    );
  }
}
```

- 복잡한 도메인 객체를 생성할 때 생성자 파라미터가 너무 길어지는 문제를 방지하고 의도를 명확히 표현한다.

## 4. 리뷰어를 위한 친절한 주석 및 JSDoc 가이드

> 📢 **주석의 황금률**: 코드가 **"무엇을(What)"** 하는지는 코드 자체로 드러내고, 주석은 **"왜(Why)" 이렇게 작성했는지 배경과 비즈니스 의도**를 설명한다.

```typescript
/**
 * 태스크에 속한 모든 루프의 완료 상태를 검증하는 루프 가드(Loop Guard) 함수.
 * 
 * [설계 배경 및 이유]
 * 루프가 미완료(보완 또는 보류) 상태로 남아있는 상태에서 태스크가 정리되면

 */
export function assertAllLoopsResolved(loops: LoopEntity[]): void {
  // ...

## 5. 도메인 중심 테스트 작성 지침 (Test-Driven)

### 5.1 테스트 디렉토리 계층 구조 원칙
소스 트리(`src/`)는 순수 실행 코드만 유지하며, 모든 테스트는 `test/` 루트 아래에서 **인프라/에이전트(`test/agent/`)**와 **비즈니스 서비스(`test/service/`)**로 명확히 분리하고, 도메인별 하위 패키지에 `unit/`과 `integration/`을 배치합니다.

```
test/
├── agent/                       # 에이전트 / 하네스 인프라 테스트
│   ├── unit/                    # 고속 단위 테스트 (Mocking / No DB)
│   │   ├── agent-domain.test.ts
│   │   ├── agent-service.test.ts
│   │   ├── agent-api.test.ts
│   │   └── docs-scanner.test.ts
│   └── integration/             # Drizzle ORM DB 연동 통합 테스트
│       └── agent-drizzle-repository.integration.test.ts
│
└── service/                     # 비즈니스 서비스 도메인 테스트
    ├── auth/                    # 인증 도메인 (Auth / Kakao)
    │   ├── unit/
    │   │   ├── auth-domain.test.ts

    │   ├── unit/

    │   │   ├── mvp1-review-kakao-server.test.ts

### 5.2 테스트 작성 규칙
1. **테스트 네이밍**: 한글로 명확한 의도와 기댓값을 작성한다 (`it('미완료 루프가 존재하면 태스크 정리를 거부한다', () => { ... })`).
2. **Given - When - Then 패턴**:
   - **Given (준비)**: 테스트할 도메인 객체 및 조건 설정
   - **When (실행)**: 검증 대상 비즈니스 메서드 호출
   - **Then (검증)**: 결과 상태 및 예외 발생 여부 확인
3. **독립성 (No External DB)**: 단위 테스트(`unit/`)는 DB 연결 없이 메모리에서 1밀리초 이내로 실행되어야 한다.

```typescript
describe('TaskEntity - 루프 가드 도메인 규칙', () => {
  it('미완료 루프가 남아있으면 clean() 호출 시 LoopGuardViolationException 예외가 발생해야 한다', () => {
    // Given (준비)
    const task = new TaskEntity('TSK-01', 'SES-01', '인증구현', '처리');
    const runningLoop = new LoopEntity('LP-01', 'TSK-01', '단위테스트작성', '처리');
    task.addLoop(runningLoop);

    // When & Then (실행 및 예외 검증)
    expect(() => task.clean('요약')).toThrowError(LoopGuardViolationException);
    expect(task.status).toBe('처리'); // 상태가 변하지 않고 보호되어야 함
  });
});
```
