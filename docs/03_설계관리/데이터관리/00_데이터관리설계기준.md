# 00. 데이터관리 설계기준

## 1. 목적

PDFowers의 테이블, 컬럼, 코드, 도메인, 메타정보 설계 기준을 정의한다. 본 문서는 기존 PDFrend 데이터관리 기준을 PDFowers 신규 프로젝트에 맞게 승계하되, 하네스 기반 구현과 PostgreSQL/ORM 적용 가능성을 함께 고려한다.

참고 원문: [PDFrend 데이터관리개요](https://github.com/jkoogit/PDFrend/blob/main/docs/03_%EC%84%A4%EA%B3%84%EA%B4%80%EB%A6%AC/%EB%8D%B0%EC%9D%B4%ED%84%B0%EA%B4%80%EB%A6%AC/00_%EB%8D%B0%EC%9D%B4%ED%84%B0%EA%B4%80%EB%A6%AC%EA%B0%9C%EC%9A%94.md)

## 2. 사전 체계

| 사전 | 책임 | 적용 방식 |
| :--- | :--- | :--- |
| 단어사전 | 허용 단어와 금지 축약어 관리 | `usr` 같은 임의 축약어를 금지하고 `user`처럼 표준 단어를 사용 |
| 용어사전 | 업무 의미가 있는 컬럼/속성 명칭 관리 | `login_id`, `provider_user_id`, `email_verified_at`처럼 업무 의미를 고정 |
| 도메인사전 | 물리 타입, 길이, 제약 관리 | `uuid`, `text_100`, `status_cd`, `yn` 등 저장 규격 정의 |
| 공통코드사전 | 상태, 유형, 이벤트 코드의 허용 값 관리 | `USER_STATUS_ACTIVE`, `AUTH_PROVIDER_KAKAO` 같은 코드값과 라벨 분리 |

사전 변경 시 테이블 설계 문서, ORM 스키마, 테스트 데이터, API 명세를 함께 현행화한다.

## 3. 명명 규칙

| 항목 | 규칙 | 예시 |
| :--- | :--- | :--- |
| 테이블명 | 도메인 또는 업무 집합을 복수형보다 단수 개념으로 명확히 표현 | `user_account`, `auth_identity`, `account_merge_request` |
| 컬럼명 | 업무 접두 또는 소유 개념 + 표준 용어 | `user_uuid`, `provider_user_id`, `merge_status_cd` |
| 식별자 | UUID 내부 식별자는 `_uuid` 접미사를 사용 | `user_uuid`, `auth_identity_uuid`, `verified_email_uuid` |
| 외부 원문 ID | 외부 시스템이 제공한 원문 식별자는 의미 보존을 위해 `_id` 허용 | `provider_user_id`, `login_id` |
| 상태 코드 | 상태 의미 컬럼은 `_status_cd` 접미사 사용 | `user_status_cd`, `merge_status_cd` |
| 유형 코드 | 유형 의미 컬럼은 `_type_cd` 접미사 사용 | `audit_event_type_cd` |
| 여부값 | DB 저장은 boolean을 우선 사용하고 외부 연계만 Y/N 변환 | `email_notification_opt_in` |
| 날짜 | 날짜만 저장하는 값은 `_dt` 접미사를 사용하고 표현 기준은 `yyyymmdd`로 둔다 | `expire_dt` |
| 일시 | 시각까지 저장하는 값은 ORM 관례와 운영 가독성을 고려해 `_at`을 우선 사용한다. 기존 `dtm` 용어를 사용할 때 표현 기준은 `yyyymmdd hhmmss`다 | `created_at`, `updated_at`, `approved_at` |

`created_at`, `updated_at`은 특정 하네스의 고유 기능이 아니라 웹 애플리케이션과 ORM 생태계에서 생성 일시, 수정 일시를 표현할 때 널리 쓰는 관례적 컬럼명이다. PDFowers는 기존 데이터관리 기준의 등록/수정 메타 의미를 유지하되, 구현과 ORM 스키마의 가독성을 위해 `created_*`, `updated_*` 명명으로 통일한다.

## 4. 공통 메타 컬럼

모든 영속 테이블은 원칙적으로 다음 메타정보를 가진다.

| 컬럼 | 의미 |
| :--- | :--- |
| `created_sys` | 최초 등록 시스템 |
| `created_at` | 최초 등록 일시 |
| `created_by` | 최초 등록 사용자 또는 시스템 계정 |
| `updated_sys` | 최종 수정 시스템 |
| `updated_at` | 최종 수정 일시 |
| `updated_by` | 최종 수정 사용자 또는 시스템 계정 |
| `version` | 낙관적 잠금, 변경 충돌 감지, 동시 수정 방지를 위한 버전 |

`created_at`, `updated_at`은 ORM에서 자동 입력 또는 자동 갱신 기능을 붙이기 쉬운 이름이다. 다만 자동화 여부는 ORM 선택 후 결정하며, 시스템/사용자 컬럼과 `version`은 서비스 계층에서 명시적으로 관리한다.

| 선택지 | 장점 | 단점 | 제안 |
| :--- | :--- | :--- | :--- |
| 공통 7종 적용 | 감사성과 운영 추적, 동시 수정 제어가 명확함 | 모든 테이블 작성 시 반복 정의가 필요함 | 핵심 업무 테이블 기본안 |
| `created_at/updated_at`만 사용 | 구현이 가장 단순함 | 등록/수정 주체와 시스템 추적이 약함 | 임시 테이블 또는 테스트 전용 |
| ORM 자동 메타 + 서비스 주체 기록 | 자동화와 감사 추적의 균형이 좋음 | ORM별 구현 차이를 문서화해야 함 | ORM 확정 후 상세 설계 후보 |

## 5. 타입과 도메인 기준

| 도메인 | 권장 물리 타입 | 적용 대상 |
| :--- | :--- | :--- |
| `uuid` | PostgreSQL `uuid` | `user_uuid`, `auth_identity_uuid`, `verified_email_uuid` 같은 내부 식별자 |
| `id_num` | bigint 또는 generated identity | 내부 단순 증가 식별자 후보 |
| `external_id` | varchar | 제공자 ID, 외부 시스템 ID |
| `status_cd` | varchar(50) 또는 공통코드 FK | 사용자 상태, 병합 요청 상태 |
| `type_cd` | varchar(50) 또는 공통코드 FK | 인증 제공자, 감사 이벤트 유형 |
| `yn` | boolean | 수신 동의, 사용 여부, 삭제 여부 |
| `dt` | char(8) 또는 date | 날짜 값. 표현 기준은 `yyyymmdd` |
| `dtm` | timestamp with time zone | 일시 값. 문서 표현 기준은 `yyyymmdd hhmmss` |
| `text_100` | varchar(100) | 표시명, 짧은 라벨 |
| `text_500` | varchar(500) | 이메일, URL, 사유 |
| `text_1000` | varchar(1000) | 긴 설명, 사용자 안내문 |
| `json_data` | jsonb | 감사 로그 메타데이터, 제공자 원본 일부 |

PostgreSQL은 `uuid`를 내장 지원하므로 내부 식별자는 UUID 타입을 기본 후보로 둔다. UUID 타입 컬럼명은 `_uuid` 접미사로 통일하며, 사용자가 직접 입력하는 `login_id`와 외부 제공자가 발급한 `provider_user_id`는 원문 의미 보존을 위해 `_id`를 유지한다.

## 6. 코드 정책

상태와 유형은 DB에 표시 문자열을 직접 저장하지 않는다. DB에는 코드값을 저장하고 화면에는 공통코드 라벨을 표시한다.

| 코드 그룹 | 코드 예시 | 사용 위치 |
| :--- | :--- | :--- |
| `USER_STATUS` | `ACTIVE`, `MERGED`, `SUSPENDED`, `DELETED` | `user_account.user_status_cd` |
| `AUTH_PROVIDER` | `LOCAL`, `EMAIL`, `KAKAO`, `NAVER`, `GOOGLE` | `auth_identity.provider_cd` |
| `MERGE_STATUS` | `REQUESTED`, `APPROVED`, `EXPIRED`, `CANCELLED`, `COMPLETED`, `FAILED` | `account_merge_request.merge_status_cd` |
| `AUDIT_EVENT_TYPE` | `LOGIN_SUCCESS`, `LOGIN_FAILURE`, `IDENTITY_LINKED`, `MERGE_APPROVED` | `audit_log.audit_event_type_cd` |

코드값은 단어형을 기본 후보로 둔다. 다국어 표시, 라벨 변경, 운영 화면 정렬은 공통코드사전에서 관리한다.

## 7. MVP1 인증 테이블 설계 기준

| 테이블 | 책임 | 핵심 제약 |
| :--- | :--- | :--- |
| `user_account` | 내부 사용자 계정 본체 | `user_uuid` PK, `user_status_cd` 공통코드 |
| `local_credential` | 삭제 불가한 기본 ID/PW 로그인 정보 | `user_uuid` 1:1, `login_id` 유니크 |
| `verified_email` | 이메일 로그인/인증/알림 대상 | `email` 유니크 후보, 인증 필수 설정이면 활성 인증 이메일 삭제 차단 |
| `auth_identity` | 간편로그인 제공자 식별자 | `(provider_cd, provider_user_id)` 유니크, 간편로그인은 모두 연결 해제 가능 |
| `account_merge_request` | 계정 통합 요청 상태 | 요청/대상 사용자, 상태 코드, 만료 일시, 승인 일시 |
| `audit_log` | 인증과 계정 통합 감사 이벤트 | 이벤트 유형 코드, 행위자, 대상, JSON 메타데이터 |

기본 로그인 정보는 ID/PW이며 사용자가 임의 삭제할 수 없다. 계정 삭제는 탈퇴 절차로 처리한다. 이메일 인증이 필수인 설정에서는 인증 완료 이메일 삭제를 차단하거나, 새 이메일 인증 완료 후 교체한다.

## 8. 보안 저장 기준

| 대상 | 저장 기준 |
| :--- | :--- |
| 비밀번호 | 원문 저장 금지, Argon2id 우선 검토 |
| OAuth Access Token | MVP1에서는 저장하지 않는 방향 우선 |
| OAuth Refresh Token | 장기 API 호출이 필요할 때만 암호화 저장 검토 |
| Authorization Code | 저장 금지, 로그 출력 금지 |
| Client Secret | DB 저장 금지, 환경변수 또는 시크릿 저장소 사용 |
| 감사 로그 메타데이터 | 토큰, 비밀번호, 인증 코드, Client Secret 포함 금지 |

비밀번호 해시는 OWASP Password Storage Cheat Sheet 기준에 따라 Argon2id를 1순위로 검토한다. Node.js/하네스 환경에서 Argon2id 운영이 어렵다면 bcrypt를 2순위로 검토하되, bcrypt의 입력 길이 제한과 비용 파라미터를 명시한다.
