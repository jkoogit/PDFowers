# 01. 헥사고날 클린 아키텍처 및 도메인 중심 테스트 가이드

## 1. 개요 및 배경

본 문서는 전통적인 3계층(Layered) 아키텍처의 한계를 극복하고, **비즈니스 도메인을 기술 인프라(DB, 웹 프레임워크, 외부 라이브러리)로부터 완벽히 격리**하여 독립적인 진화와 초고속 테스트를 가능하게 하는 **헥사고날 아키텍처(Hexagonal Architecture / Ports and Adapters)**와 **도메인 중심 테스트(Domain-Centric Testing)**의 실무 적용 지침을 제공한다.

---

## 2. 전통적 레이어드 아키텍처 vs 헥사고날 아키텍처

```mermaid
flowchart LR
    subgraph Layered [전통적 3계층 (DB 중심 의존성)]
        L1[Presentation Controller] --> L2[Business Service]
        L2 --> L3[(Database Entity & DAO)]
    end

    subgraph Hexagonal [헥사고날 클린 아키텍처 (도메인 중심 의존성)]
        H_IN[Inbound Adapter<br>Express / CLI] -->|Driving Port| H_DOMAIN((순수 비즈니스 도메인<br>Entity / VO / Policy))
        H_DOMAIN -->|Driven Port| H_OUT[Outbound Adapter<br>Drizzle / Memory DB]
    end
```

### 2.1 전통적 레이어드 아키텍처의 한계
1. **DB 주도 설계(Database-Driven Design)**: 테이블 스키마와 ORM 엔티티를 먼저 설계하고 도메인 로직을 서비스에 나열하므로 비즈니스 규칙이 흩어짐.
2. **테스트의 어려움**: 서비스 계층이 DB DAO나 특정 ORM에 강하게 결합되어 단위 테스트 시 무거운 DB 연결이나 복잡한 Mocking이 강제됨.
3. **인프라 종속성**: DB나 웹 프레임워크를 교체하기 매우 어려움.

### 2.2 헥사고날(포트와 어댑터) 아키텍처의 해결책
1. **의존성 역전 원칙 (DIP)**: 비즈니스 도메인은 바깥쪽(DB, Web)을 전혀 알지 못하며, 오직 자신이 정의한 **인터페이스(포트, Port)**만 바라본다.
2. **기술의 부품화 (Pluggable Adapters)**: DB(Drizzle ➔ Prisma ➔ In-Memory), 웹(Express ➔ Fastify ➔ CLI)을 손쉽게 갈아 끼울 수 있다.

## 3. 포트(Port)와 어댑터(Adapter)의 분류 및 구조

```
[외부 세계]               [포트 계층 (인터페이스)]             [코어 도메인]
웹 요청 (HTTP)      ──►  인바운드 포트 (Inbound / UseCase) ──►  비즈니스 도메인 모델
                         (예: TaskUseCase)                     (Session/Task/Loop)
                                                                    │
DB / 파일시스템     ◄──  아웃바운드 포트 (Outbound / SPI)    ◄──────┘
                         (예: AgentRepositoryPort)
```

| 포트 구분 | 성격 | 정의 위치 | 역할 | 예시 |
| :--- | :--- | :--- | :--- | :--- |
| **인바운드 포트 (Inbound Port)** | **Driving Port**<br>(시스템을 움직임) | `ports/in/` | 애플리케이션이 외부(사용자/API)에 제공하는 유스케이스 진입점 인터페이스 | `StartSessionUseCase`, `CleanTaskUseCase` |
| **아웃바운드 포트 (Outbound Port)** | **Driven Port**<br>(시스템이 사용함) | `ports/out/` | 도메인이 필요로 하는 외부 인프라 기능(DB 저장, 파일 스캔) 인터페이스 | `AgentRepositoryPort`, `DocsScannerPort` |
| **인바운드 어댑터** | Driving Adapter | `adapters/in/` | HTTP 요청, CLI 명령을 해석하여 인바운드 포트를 호출 | `ExpressAgentController`, `HarnessCliAdapter` |
| **아웃바운드 어댑터** | Driven Adapter | `adapters/out/` | 아웃바운드 포트 인터페이스를 실제 기술(Drizzle, In-Memory)로 구현 | `DrizzleAgentRepository`, `MemoryAgentRepository` |

## 4. 도메인 중심 테스트(Domain-Centric Testing) 전략

### 4.1 3계층 테스트 피라미드

```
      / \
     /   \      1. 통합/E2E 테스트 (어댑터 및 실제 Express/DB 연동 검증)
    /     \
   /-------\    2. 애플리케이션 서비스 테스트 (인메모리 레포지토리 기반 유스케이스 검증)
  /         \
 /-----------\  3. 순수 도메인 단위 테스트 (엔티티 상태머신, 루프가드, 비즈니스 규칙 검증) -> 80% 비중
```

### 4.2 초고속 테스트를 위한 테스트 더블 (In-Memory Fake Adapter)
- 무거운 PostgreSQL을 매번 띄우지 않고, `AgentRepositoryPort`를 구현한 `MemoryAgentRepository`를 사용하여 수 밀리초 만에 수백 개의 유스케이스 테스트를 완수한다.

```typescript
// test/unit/agent-service.test.ts
describe('AgentApplicationService - 헥사고날 테스트', () => {
  let service: AgentApplicationService;
  let fakeRepo: MemoryAgentRepository;

  beforeEach(() => {
    // 실제 DB 대신 인메모리 아웃바운드 어댑터 주입 (초고속 실행)
    fakeRepo = new MemoryAgentRepository();
    service = new AgentApplicationService(fakeRepo);
  });

  it('세션 시작 유스케이스가 성공적으로 수행되어야 한다', async () => {
    const result = await service.startSession({
      sessionId: 'SES-01',
      sessionName: '테스트 세션',
      workGroup: ['개발'],
      agent: 'gemini',
      model: 'gemini-3.7-flash'
    });

    expect(result.status).toBe('시작');
    const saved = await fakeRepo.findSessionById('SES-01');
    expect(saved).toBeDefined();
  });
});
```

## 5. PDFowers 프로젝트 디렉토리 매핑 가이드 (소스 & 테스트 패키지 구조)

- **`src/`**: 오직 프로덕션 런타임 소스 코드만 배치합니다. 에이전트 서비스는 `src/agent/` 자립형(Self-contained) 모듈로 격리됩니다.
- **`test/`**: 모든 테스트 코드를 배치하며, **인프라/에이전트(`test/agent/`)**와 **비즈니스 서비스(`test/service/`)**로 명확히 분리하고 도메인별 하위 패키지에 `unit/`과 `integration/`을 구성합니다.

```
src/
├── agent/                       # 에이전트 / 하네스 자립형 모듈
│   ├── domain/                  # 1. 순수 도메인 (외부 기술 의존성 0%)
│   │   ├── model.ts             # 엔티티, VO (SessionEntity, TaskEntity, LoopEntity, TokenUsage)
│   │   ├── state-machine.ts     # 상태 전이 머신 및 루프 가드(Loop Guard)
│   │   └── reconciler.ts        # 상시 자가 치유(Reconciler) 도메인 서비스
│   ├── ports/                   # 2. 포트 인터페이스 (경계 정의)
│   │   ├── in/agent-usecases.ts # 인바운드 유스케이스 인터페이스
│   │   └── out/
│   │       ├── agent-repository.port.ts # 아웃바운드 영속성 포트 인터페이스
│   │       └── docs-scanner.port.ts     # 아웃바운드 문서 스캐너 포트 인터페이스
│   ├── service/                 # 3. 애플리케이션 서비스 (오케스트레이션)
│   │   └── agent-application-service.ts # 포트 기반 유스케이스 구현체
│   ├── adapters/                # 4. 어댑터 (기술 구현체)
│   │   ├── in/web/agent-controller.ts # Native node:http REST 라우터/컨트롤러
│   │   └── out/
│   │       ├── persistence/
│   │       │   ├── memory-agent-repository.ts  # 초고속 단위테스트용 인메모리 어댑터
│   │       │   └── drizzle-agent-repository.ts # 프로덕션 PostgreSQL/Drizzle 어댑터
│   │       └── filesystem/
│   │           └── local-docs-scanner.ts       # 로컬 마크다운 문서 스캐너 어댑터
│   ├── agent-api-smoke-check.ts # 단독 스모크 검증 실행기
│   └── index.ts                 # 에이전트 모듈 진입점
├── db/                          # DB 스키마 및 마이그레이션
├── domains/                     # 비즈니스 도메인 (auth 등)
└── review/                      # 검토 도메인

test/
├── agent/                       # 에이전트 / 하네스 인프라 테스트
│   ├── unit/                    # 고속 단위 테스트 (Mocking / No DB)
│   │   ├── agent-domain.test.ts # 도메인 엔티티 & 루프가드 & 상태머신 테스트
│   │   ├── agent-service.test.ts # 유스케이스 오케스트레이션 테스트
│   │   ├── agent-api.test.ts    # REST API 핸들러 테스트
│   │   └── docs-scanner.test.ts # 로컬 마크다운 스캐너 테스트
│   └── integration/             # DB/인프라 통합 테스트
│       └── agent-drizzle-repository.integration.test.ts # Drizzle 연동 통합 테스트
│
└── service/                     # 비즈니스 서비스 도메인 테스트
    ├── auth/                    # 인증 도메인
    │   ├── unit/                # auth-domain, kakao-oauth, kakao-config 등
    │   └── integration/         # auth-repository 통합 테스트
    ├── review/                  # 검토 도메인
    │   ├── unit/                # mvp1-review-server, merge-ux, notifications 등
    │   └── integration/         # mvp1-review-persistence 통합 테스트
    └── common/                  # 공통 유틸 도메인
        └── unit/                # database-url, common-code-seed, smtp 등
```
