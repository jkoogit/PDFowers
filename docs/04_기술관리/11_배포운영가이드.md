# 11. 배포 운영 가이드

## 목적

PDFowers MVP1 검수 서버를 dev, stg, prd 환경에서 일관되게 실행하기 위한 배포 기준을 정리한다. dev 애플리케이션은 NAS Docker Compose로 운영하고, dev DB는 별도 우분투 PostgreSQL 서비스를 사용한다. stg와 prd는 Cloudtype에서 Dockerfile 기반으로 운영한다.

## 현재 브랜치 현행화 상태

2026-06-11 세션 시작 점검 기준으로 원격 브랜치의 커밋 SHA는 서로 다르지만 파일 내용 tree hash는 동일하다.

| 브랜치 | 커밋 SHA 상태 | tree hash 상태 | 판단 |
| :--- | :--- | :--- | :--- |
| `origin/dev` | `origin/stg`, `origin/main`과 다름 | 동일 | 파일 내용 현행화 완료 |
| `origin/stg` | `origin/dev`, `origin/main`과 다름 | 동일 | 파일 내용 현행화 완료 |
| `origin/main` | `origin/dev`, `origin/stg`와 다름 | 동일 | 파일 내용 현행화 완료 |

커밋 SHA 차이는 승급 머지 커밋 이력 차이에서 발생할 수 있다. 이후에는 브랜치 포인터를 강제로 맞추지 않고 PR 기반 승급 절차로 이력을 남긴다.

## 승급 원칙

| 단계 | PR 방향 | 검증 기준 |
| :--- | :--- | :--- |
| 작업 반영 | `task/* -> dev` | `npm run typecheck`, `npm run test:unit`, 필요한 통합 테스트 |
| 검증 승급 | `dev -> stg` | stg Cloudtype 배포, 카카오 callback, DB migration 확인 |
| 운영 승급 | `stg -> main` | prd Cloudtype 배포 전 최종 검수, 이슈 댓글에 SHA와 검증 결과 기록 |

승급은 GitHub PR로만 처리한다. 직접 push나 브랜치 포인터 강제 변경으로 `dev`, `stg`, `main`을 맞추지 않는다.

## dev NAS Docker 구성

dev 애플리케이션 컨테이너는 NAS Docker Station에 `deploy/nas/docker-compose.dev.yml` 파일 하나를 올려 실행한다. QNAP Container Station의 Docker Build 환경에는 `git` 실행 파일이 없어 GitHub URL build context를 직접 사용할 수 없다. 따라서 GitHub Actions가 `dev` 브랜치 이미지를 GHCR에 발행하고, NAS는 이미지를 pull해서 실행한다.

```yaml
image: ghcr.io/jkoogit/pdfowers:dev
```

Docker Station에서 환경변수 파일을 함께 지정할 수 있으면 `deploy/nas/.env.example`을 복사해 실제 값으로 바꾼 `.env`를 사용한다.

```bash
cp deploy/nas/.env.example deploy/nas/.env
docker compose --env-file deploy/nas/.env -f deploy/nas/docker-compose.dev.yml pull
docker compose --env-file deploy/nas/.env -f deploy/nas/docker-compose.dev.yml up -d
```

`deploy/nas/.env`에는 우분투 PostgreSQL 접속용 `DATABASE_URL`과 카카오 Client Secret을 기록한다. 이 파일은 Git에 커밋하지 않는다.

GHCR 패키지가 private 상태라면 NAS에서 먼저 `docker login ghcr.io`를 수행하거나 GitHub Packages 접근 토큰을 Container Station registry 인증정보에 등록한다. 외부 인증 없이 운영하려면 `ghcr.io/jkoogit/pdfowers` 패키지를 public으로 공개한다.

### QNAP Container Station dev 배포 기준

dev 이미지는 `ghcr.io/jkoogit/pdfowers:dev` 같은 고정 태그를 사용한다. 같은 태그에 새 이미지가 발행되면 실행 중인 컨테이너는 자동으로 새 이미지로 바뀌지 않는다. 따라서 새 dev 이미지를 반영하려면 이미지를 pull한 뒤 컨테이너를 새 이미지 기준으로 교체해야 한다.

권장 순서는 다음과 같다.

1. GitHub Actions에서 `dev` 이미지 발행 완료를 확인한다.
2. Container Station 또는 CLI에서 `ghcr.io/jkoogit/pdfowers:dev` 이미지를 pull한다.
3. compose 기준으로 `up -d`를 실행해 이미지 ID 또는 환경변수가 바뀐 경우에만 컨테이너가 교체되게 한다.
4. `/auth/kakao/config-status`와 `/auth/kakao/start` redirect를 확인한다.

CLI를 사용할 수 있으면 `--force-recreate` 없이 아래 명령을 우선 사용한다.

```bash
docker compose --env-file deploy/nas/.env -f deploy/nas/docker-compose.dev.yml pull pdfowers_dev
docker compose --env-file deploy/nas/.env -f deploy/nas/docker-compose.dev.yml up -d pdfowers_dev
```

Container Station UI만 사용할 때의 `Recreate`는 새 이미지 또는 환경변수 변경을 반영해야 하는 경우에는 정상적인 교체 절차다. 다만 이미지 ID와 환경변수가 모두 같을 때 반복 실행하는 것은 불필요하다. 앱 컨테이너는 무상태이고 DB는 외부 우분투 PostgreSQL에 있으므로 컨테이너 교체 자체가 데이터 삭제를 의미하지는 않지만, 매번 강제 재생성을 기본 절차로 두기보다는 `이미지 pull -> 변경 시 교체 -> smoke 검증` 순서로 운영한다.

### NAS 서비스

| 서비스 | 컨테이너 | 기본 포트 | 용도 |
| :--- | :--- | :---: | :--- |
| PDFowers dev | `pdfowers_dev` | `4173` | MVP1 검수 서버 |

DB는 NAS 컨테이너로 실행하지 않는다. 앱 컨테이너의 `DATABASE_URL`은 우분투에 설치된 PostgreSQL 서비스 주소를 가리켜야 한다.

```dotenv
DATABASE_URL=postgresql://<ubuntu-db-user>:<ubuntu-db-password>@<ubuntu-db-host>:<ubuntu-db-port>/<ubuntu-db-name>
```

우분투 PostgreSQL 방화벽과 `postgresql.conf`, `pg_hba.conf`는 NAS 서버 IP에서 접근할 수 있도록 별도로 허용한다.

### NAS 볼륨 기준

| 서비스 | 볼륨 필요 여부 | 기본 경로 | 이유 |
| :--- | :---: | :--- | :--- |
| PDFowers dev | 불필요 | 없음 | MVP1 검수 상태는 DB에 저장하고 컨테이너는 무상태로 재생성 가능 |
| 우분투 PostgreSQL | NAS compose 대상 아님 | 우분투 DB 서버 정책에 따름 | DB는 우분투 설치 서비스를 사용 |

PDF 업로드, 변환 파일, 캐시 같은 파일 저장 기능이 추가되면 PDFowers 앱 컨테이너에도 `/app/data` 또는 별도 스토리지 경로를 bind mount로 추가한다. MVP1 인증 검수 범위에서는 앱 볼륨을 두지 않는다.

## DB Migration

각 환경의 `DATABASE_URL`을 주입한 상태에서 Drizzle migration을 적용한다.

```bash
npm run db:migrate
```

Cloudtype에서 one-off command 실행이 어렵다면 운영자 PC 또는 NAS에서 같은 `DATABASE_URL`을 일시 주입해 실행한다. 민감정보가 터미널 기록, 이슈, PR 본문에 남지 않도록 한다.

## dev 도메인 임시 운영

2026-06-14 기준 dev NAS에서는 QNAP DDNS 도메인에 대한 Let's Encrypt 인증서 발급이 확인되었다. `fowersdev.pdfrend.com` 커스텀 도메인은 QNAP 내장 인증서 관리에서 ACME challenge가 안정적으로 처리되지 않아 정식 연결을 보류한다.

개발 검수는 우선 QNAP DDNS 도메인 HTTPS를 사용한다. 카카오 개발자 콘솔의 dev Redirect URI도 실제로 접속 가능한 QNAP DDNS 도메인 기준으로 맞춘다.

앱 환경변수는 도메인과 path를 분리한다. 기본 callback path는 `/auth/kakao/callback`이며, 일반적으로 환경별로 `APP_BASE_URL`만 바꾼다.

```dotenv
APP_BASE_URL=https://jkok2.myqnapcloud.com:4443
KAKAO_REDIRECT_PATH=/auth/kakao/callback
```

위 설정은 런타임에서 다음 Redirect URI로 조합된다.

```text
https://jkok2.myqnapcloud.com:4443/auth/kakao/callback
```

`KAKAO_REDIRECT_URI`가 있으면 하위 호환을 위해 그 값을 우선한다. 신규 배포에서는 `KAKAO_REDIRECT_URI`를 비워두고 `APP_BASE_URL`을 기준으로 관리한다.

운영서비스 또는 커스텀 dev 도메인 연결 시점에는 다음 중 하나를 다시 결정한다.

| 선택지 | 내용 |
| :--- | :--- |
| Cloudtype 유지 | 운영 도메인과 인증서를 Cloudtype에서 관리 |
| NAS 앞단 Nginx/NPM 도입 | NAS 80/443, Let's Encrypt, `4173` 프록시를 Nginx 또는 Nginx Proxy Manager가 담당 |
| 별도 ACME 발급 | DNS-01 등으로 인증서를 발급한 뒤 QNAP에 가져오기 |

## 민감정보 관리

- DB 비밀번호, pgAdmin 비밀번호, OAuth Client Secret은 Git, 이슈, PR, 문서에 원문으로 기록하지 않는다.
- 저장소에는 `.env.example` 같은 placeholder만 둔다.
- 실제 `.env`는 NAS 또는 Cloudtype 시크릿 저장소에서만 관리한다.
- OAuth access token과 refresh token은 MVP1에서 저장하지 않는다.

## 2026-06-17 Kakao Redirect URI 환경 분리

Kakao Redirect URI는 `APP_ENV`에 따라 분리한다.

- `APP_ENV=dev`: `KAKAO_ALLOWED_REDIRECT_ORIGINS`에 등록된 요청 Host를 기준으로 Redirect URI를 만든다.
- `APP_ENV=stg`, `APP_ENV=prd`: `APP_BASE_URL`과 `KAKAO_REDIRECT_PATH`를 조합한 고정 Redirect URI를 사용한다.

dev NAS 예시:

```dotenv
APP_ENV=dev
APP_BASE_URL=https://jkok2.myqnapcloud.com:4443
KAKAO_REDIRECT_PATH=/auth/kakao/callback
KAKAO_ALLOWED_REDIRECT_ORIGINS=http://localhost:4173,http://127.0.0.1:4173,http://192.168.219.112:4173,https://jkok2.myqnapcloud.com:4443
```

stg/prd에서는 `KAKAO_ALLOWED_REDIRECT_ORIGINS`를 설정하더라도 request-host redirect를 사용하지 않는다. 운영 환경은 Host 헤더에 따라 OAuth callback이 바뀌지 않도록 `APP_BASE_URL` 기준을 유지한다.
## 2026-06-17 Kakao dev 배포 검증 기준

dev NAS의 우선 기준 URL은 `https://jkok2.myqnapcloud.com:4443`이다.

```dotenv
APP_BASE_URL=https://jkok2.myqnapcloud.com:4443
KAKAO_REDIRECT_PATH=/auth/kakao/callback
```

배포 후에는 다음 검사를 통과해야 한다.

```powershell
npm run review:kakao-smoke -- --base-url https://jkok2.myqnapcloud.com:4443
```

검사는 두 단계를 확인한다.

1. `/auth/kakao/config-status`가 `enabled=true`, `missing=[]`를 반환한다.
2. `/auth/kakao/start`가 `https://kauth.kakao.com/oauth/authorize`로 3xx redirect를 반환한다.

NAS compose healthcheck도 같은 smoke check를 컨테이너 내부 URL `http://127.0.0.1:4173`로 실행한다. 이 검사는 외부 카카오 로그인 완료까지 자동화하지 않고, 배포된 서버가 카카오 로그인 화면으로 이동 가능한 authorize URL을 만들 수 있는지 확인한다.
