# 04. 기술관리

## 목적

신규 프로젝트의 기술 스택, 구현 규칙, 외부 API 연동, 인증, 스토리지, 개발 도구를 관리한다.

## 기존 참고 문서에서 확인한 기술 후보

| 영역 | 기존 후보 |
| :--- | :--- |
| 런타임 | Node.js 22.13.0 |
| 언어 | TypeScript |
| 백엔드 | Express.js, tRPC, Zod, SuperJSON |
| 프론트엔드 | React 19, Tailwind CSS 4, shadcn/ui, Vite, PDF.js |
| DB | PostgreSQL, Drizzle ORM |
| 실시간 | WebSocket 또는 Socket.io |
| 테스트 | Vitest, Testing Library, Playwright |
| 인증 | Manus OAuth, Passport.js, 카카오/네이버/구글 OAuth, 이메일 인증 |
| 스토리지 | NAS/Ubuntu 로컬 디스크, S3 계열 저장소, 추상화 계층 |

## 하네스 전환 기준

기존 기술 후보는 그대로 확정하지 않는다. 하네스 기반 신규 프로젝트에서는 다음 순서로 확정한다.

1. 도메인 기준 아키텍처와 하네스 생성 구조의 충돌 여부를 확인한다.
2. 기본 서버/클라이언트 통신 방식과 REST/OpenAPI, tRPC, 서버 액션 도입 필요성을 비교한다.
3. DB와 ORM을 PostgreSQL, Drizzle, Prisma, Kysely 등 범용 후보 중 선택한다.
4. 인증은 서버 세션, JWT, Passport.js, 직접 OAuth 클라이언트, 인증 전문 라이브러리를 비교하여 결정한다.
5. 스토리지는 로컬 디스크, 오브젝트 스토리지, 하네스 제공 저장소 중 운영 비용과 백업 가능성을 기준으로 결정한다.

## 초기화 기준

기존 Node.js/tRPC/Drizzle 문서는 우선 후보로만 남긴다. 하네스가 다른 표준을 제공하면 신규 프로젝트의 생산성과 유지보수성을 기준으로 재선택한다.

## 검토 필요사항

- REST/OpenAPI, tRPC, 서버 액션 중 PDFowers 서비스 특성에 맞는 API 방식을 결정해야 한다.
- 서버 세션, JWT, Passport.js, 직접 OAuth 클라이언트, 인증 전문 라이브러리를 비교해 인증 방식을 결정해야 한다.
- ORM 사용은 긍정 방향으로 두되 Drizzle, Prisma, Kysely 후보를 데이터관리 기준과 함께 비교해야 한다.
- 외부 OAuth 제공자별 전화번호/이메일 제공 정책은 최신 공식 문서로 재확인해야 한다.
- PDF 병합/주석 호환성은 실제 라이브러리 후보를 선정한 뒤 PoC가 필요하다.
