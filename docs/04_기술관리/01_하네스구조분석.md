# 01. 하네스 구조 분석

## 목적

하네스 기반 신규 프로젝트의 아키텍처, 패키지 구조, 기술 선택지를 개발 착수 전에 비교한다. 본 문서에서 말하는 하네스는 특정 에이전트 전용 기술이 아니라 프로젝트 생성과 검증을 돕는 작업 기반을 뜻한다. 구현 기술은 범용 기술을 우선 비교하고, 하네스가 생성한 구조는 제약과 참고값으로만 확인한다.

## 분석 원칙

- 기존 Node.js, Express, tRPC, Drizzle 후보는 확정값이 아니라 비교 후보로 본다.
- 특정 에이전트나 생성 도구에 종속되는 인증/데이터/API 구조는 피한다.
- 폴더와 패키지는 도메인 응집도, 변경 거리, 결합도를 기준으로 구성한다.
- 하네스가 생성한 기본 구조가 있더라도 범용 기술과 서비스 특성에 맞춰 채택 여부를 다시 결정한다.

## 아키텍처 선택지

| 선택지 | 구조 | 장점 | 단점 | 제안 |
| :--- | :--- | :--- | :--- | :--- |
| 도메인 모듈형 모놀리식 | 하나의 앱 안에서 `auth`, `document`, `annotation` 등 도메인별 모듈 분리 | MVP 속도와 도메인 경계의 균형이 좋고 배포가 단순함 | 모듈 경계 규칙을 지키지 않으면 금방 레이어가 섞임 | 1차 MVP 기본안 |
| 레이어드 모놀리식 | `controllers`, `services`, `repositories`처럼 기술 계층별 분리 | 익숙하고 초반 진입이 쉬움 | 한 기능 변경 시 여러 폴더를 오가며 변경 거리가 길어짐 | 작은 예제 외에는 비권장 |
| 패키지/워크스페이스 분리 | `apps/web`, `apps/api`, `packages/domain`, `packages/db` 분리 | 타입 공유와 독립 테스트가 좋고 장기 확장에 유리 | 초기 설정과 빌드 구성이 무거움 | 하네스가 워크스페이스를 잘 지원하면 검토 |
| 마이크로서비스 | 인증, 문서, 처리 작업을 별도 서비스로 분리 | 독립 배포와 확장 가능 | MVP 단계에서는 운영 복잡도가 과도함 | 후속 MVP 전까지 보류 |

1차 MVP는 도메인 모듈형 모놀리식을 우선 제안한다. 인증/계정 통합은 트랜잭션과 데이터 일관성이 중요하고, 아직 서비스 경계를 나눌 만큼 부하나 조직 경계가 없다.

## 도메인 기준 패키지 구조 후보

```text
src/
  app/                  # 앱 부트스트랩, 라우팅 연결, 전역 설정
  domains/
    auth/
      model/            # User, LocalCredential, AuthIdentity, AccountMergeRequest
      usecase/          # 회원가입, 로그인, 로그인수단 연결, 계정통합
      port/             # OAuthClient, PasswordHasher, AuthSessionStore
      adapter/          # DB, OAuth 제공자, 메일/알림 어댑터
      api/              # HTTP 또는 RPC 엔드포인트
      test/             # 도메인 단위/통합 테스트
    audit/
    document/
  shared/
    config/
    errors/
    validation/
    crypto/
  infrastructure/
    db/
    queue/
    logger/
```

도메인 내부에서는 `model -> usecase -> port -> adapter/api` 방향으로 의존성을 제한한다. 도메인 간 직접 DB 접근은 금지하고, 필요한 경우 유스케이스 또는 이벤트로 연결한다.

## API 기술 선택지

| 선택지 | 장점 | 단점 | 제안 |
| :--- | :--- | :--- | :--- |
| REST + OpenAPI | 범용성이 높고 외부 연동, 문서화, 테스트 도구가 풍부함 | 타입 공유를 별도 생성 도구로 관리해야 함 | 외부 공개 가능성을 고려하면 가장 안정적인 기본안 |
| tRPC | TypeScript 풀스택에서 타입 공유가 강력하고 개발 속도가 빠름 | 비 TypeScript 클라이언트와 공개 API 문서화가 약함 | 내부 앱 전용 API에는 유력하나, 외부 연동 가능성이 있으면 보조 후보 |
| GraphQL | 클라이언트 조회 유연성이 높음 | 인증/계정 통합 같은 명령형 흐름에는 과함 | MVP1에는 비권장 |
| 서버 액션/프레임워크 내장 RPC | 화면과 서버 구현 거리가 짧음 | 프레임워크 종속이 강하고 API 경계가 흐려질 수 있음 | 관리자/단순 폼에는 가능하나 핵심 인증 API에는 신중 |

현재 제안은 REST + OpenAPI를 1순위, tRPC를 내부 클라이언트 전용 2순위로 두는 것이다. PDFowers는 장기적으로 문서 처리, 공유 링크, 외부 도구 연동 가능성이 있으므로 범용 API 계약을 남기는 편이 유리하다.

## 서버 프레임워크 선택지

Express.js는 Node.js 생태계에서 가장 보편적인 HTTP 서버 프레임워크 중 하나다. MVP 초기에는 단순하고 자료가 많다는 장점이 있지만, 전체 시스템 관점에서는 모듈 구조, 타입 안정성, 검증 파이프라인, OpenAPI 생성 전략을 별도로 설계해야 한다.

| 선택지 | 장점 | 단점 | MVP 적합성 | 전체 시스템 적합성 |
| :--- | :--- | :--- | :--- | :--- |
| Express.js | 생태계가 크고 학습 비용이 낮으며 OAuth/세션 예제가 많음 | 구조를 강제하지 않아 도메인 경계가 쉽게 흐려질 수 있음 | 빠른 MVP에 적합 | 도메인 모듈 규칙과 OpenAPI 도구를 별도로 붙이면 가능 |
| Fastify | 성능, 플러그인 구조, 스키마 기반 검증이 강함 | Express 대비 팀 익숙도와 예제 풀이 적을 수 있음 | 하네스가 지원하면 적합 | API 서버 장기 운영 후보 |
| NestJS | 모듈, DI, 가드, 파이프 등 대규모 구조화에 강함 | 초기 보일러플레이트와 프레임워크 학습 비용이 큼 | MVP 단순 구현에는 다소 무거움 | 전체 시스템 규모가 커지면 유력 |
| 프레임워크 내장 서버 | Next.js 등 화면 프레임워크와 결합이 쉬움 | API 경계와 배포 독립성이 약해질 수 있음 | 간단한 폼/관리 기능에 적합 | 핵심 인증/PDF 처리 API에는 신중 |

MVP 초기에는 Express.js 또는 하네스가 제공하는 단순 HTTP 서버 구성을 사용할 수 있다. 다만 라우터에 업무 로직을 직접 넣지 않고 `domains/*/usecase`를 호출하는 얇은 API 어댑터로 제한해야 한다. 전체 시스템에서는 REST + OpenAPI 계약을 유지한 상태에서 Fastify 또는 NestJS로 전환 가능하도록, 도메인 유스케이스와 저장소 포트를 프레임워크 밖에 둔다.

## 인증 기술 선택지

하네스가 생성한 인증 보일러플레이트가 있다면 확인 대상일 뿐, 구현 방식을 확정하는 기준은 아니다. 구현 결정은 아래 범용 선택지를 비교해 내린다.

| 선택지 | 장점 | 단점 | 제안 |
| :--- | :--- | :--- | :--- |
| 서버 세션 + 직접 OAuth 클라이언트 | OAuth `state`, 계정 통합 승인, 로그인 상태 관리가 단순하고 특정 라이브러리 종속이 낮음 | 제공자별 OAuth 구현을 직접 관리해야 함 | MVP1 1순위 |
| Passport.js + 서버 세션 | 제공자 전략 생태계가 있고 Express와 친숙함 | 전략별 유지보수 품질 편차, 프레임워크 결합 존재 | Express 채택 시 2순위 |
| JWT 기반 인증 | 모바일/외부 API 확장에 유리하고 서버 저장 부담이 낮음 | 토큰 폐기, 계정 통합 직후 권한 반영, 보안 운영이 복잡함 | MVP1 기본안으로는 비권장 |
| 인증 전문 라이브러리 | 이메일/OAuth/세션 기능을 빠르게 구성 가능 | 라이브러리 모델에 도메인 정책을 맞춰야 할 수 있음 | 하네스/프레임워크와 잘 맞으면 검토 |
| 외부 인증 서비스 | 운영 보안 부담이 낮음 | 비용, 벤더 종속, 계정 통합 커스텀 제약 가능 | MVP1에서는 보류 |

ID/PW는 삭제 불가한 기본 로그인 수단으로 두고, 간편로그인은 모두 연결 해제 가능하게 설계한다. 이메일 인증이 필수인 경우 인증 완료 이메일은 삭제할 수 없고, 이메일 변경은 새 이메일 인증 완료 후 교체한다.

## ORM 선택지

| 선택지 | 장점 | 단점 | 제안 |
| :--- | :--- | :--- | :--- |
| Drizzle ORM | SQL 친화적이고 타입 안정성이 좋으며 마이그레이션 제어가 명확함 | 고수준 관계 API는 Prisma보다 덜 풍부함 | PostgreSQL 중심이면 유력 후보 |
| Prisma | 생산성이 높고 스키마 가독성이 좋음 | 복잡 SQL, 마이그레이션 세밀 제어, 런타임 계층이 부담일 수 있음 | 빠른 CRUD 중심이면 후보 |
| Kysely | 타입 안정 SQL 빌더로 제어력이 높음 | 스키마/마이그레이션 생태계는 별도 조합 필요 | SQL 제어를 중시하면 후보 |
| TypeORM | 데코레이터 기반이 익숙할 수 있음 | 복잡한 동작과 마이그레이션 예측성이 약할 수 있음 | 신규 프로젝트 기본안으로는 낮은 우선순위 |

ORM 사용은 긍정 방향으로 둔다. 다만 데이터관리 기준의 단어/용어/도메인/공통코드/메타 컬럼을 ORM 스키마에 반영할 수 있어야 하므로, ORM 선택 시 마이그레이션 생성물과 실제 DB 제약을 함께 검토한다.

## 비동기 처리 선택지

| 선택지 | 장점 | 단점 | 제안 |
| :--- | :--- | :--- | :--- |
| 동기 트랜잭션만 사용 | 구현이 단순하고 결과가 즉시 확정됨 | 계정 통합 후 알림/감사/대량 이전이 길어지면 응답 지연 | MVP1 최소 통합에는 가능 |
| DB Job Table | 별도 인프라 없이 비동기 재시도와 상태 추적 가능 | 고성능 큐 기능은 제한적 | MVP1 알림/후속 작업에 1순위 |
| RabbitMQ | 신뢰성 있는 메시징과 확장성이 좋음 | 운영 인프라와 모니터링 부담 증가 | PDF 처리 단계부터 재검토 |
| 인메모리 큐 | 설정이 쉽고 빠름 | 재시작 시 유실 가능 | 개발/테스트 전용 |

계정 통합 자체의 핵심 데이터 이전은 서버 트랜잭션으로 처리한다. 다만 통합 완료 알림, 감사 로그 확장, 후속 데이터 재색인, 대량 문서 소유권 이전이 생기면 DB Job Table부터 도입하는 방안을 제안한다.

PDF 처리 단계에서는 메시지 큐 도입을 재검토한다. 원본 PDF 분리, OCR, 병합 PDF 생성처럼 시간이 길고 재시도가 필요한 작업이 본격화되면 RabbitMQ 같은 외부 MQ를 후보로 올린다. 인메모리 큐는 개발/테스트 또는 단일 프로세스 보조 기능으로만 선택적으로 사용하고, 운영 필수 작업에는 유실 위험 때문에 기본안으로 두지 않는다.

## Playwright 도입 검토

Playwright는 브라우저를 실제로 구동해 사용자의 화면 흐름을 자동 검증하는 E2E 테스트 도구다.

| 항목 | 장점 | 단점 | 도입 시점 |
| :--- | :--- | :--- | :--- |
| 가입/로그인 E2E | 실제 화면, 쿠키, 리다이렉트, OAuth 모의 콜백 흐름 검증 가능 | 테스트 속도가 느리고 UI 변경에 민감함 | 로그인 화면 구현 직후 |
| PDF 뷰어 E2E | 캔버스 렌더링, 주석 상호작용 검증 가능 | 테스트 데이터와 스크린샷 안정화가 필요 | 2차/3차 MVP |
| 회귀 스모크 | 배포 전 핵심 사용자 여정 확인 가능 | 모든 케이스를 E2E로 만들면 유지비가 커짐 | MVP1부터 최소 3~5개 |

MVP1에서는 단위/통합 테스트를 주력으로 두고, Playwright는 `로그인 화면 진입 -> 미등록 계정 회원가입 이동 -> ID/PW 가입 -> 로그인 -> 인증 화면 진입` 같은 핵심 시나리오만 최소 도입한다.

## 선택 적용 시 유의사항

| 선택 영역 | 현재 선택 | 적용 시 주의사항 | 재검토 시점 |
| :--- | :--- | :--- | :--- |
| 아키텍처 | 도메인 모듈형 모놀리식 | 도메인 내부 `usecase`에 업무 규칙을 두고 API/DB 어댑터가 도메인을 침범하지 않게 한다 | 도메인별 배포나 독립 확장 필요가 생길 때 |
| API | REST + OpenAPI 우선 | OpenAPI 스키마와 실제 입력 검증 스키마가 어긋나지 않게 생성 또는 검증 절차를 둔다 | 외부 API 공개 범위가 확정될 때 |
| 서버 프레임워크 | MVP는 단순 HTTP 서버 또는 Express.js 허용 | 라우터가 비대해지지 않도록 도메인 유스케이스 호출만 담당시킨다 | API 수가 늘고 DI, 모듈 경계, 성능 요구가 커질 때 |
| 인증 | 서버 세션 + 직접 OAuth 우선 | 세션 저장소, CSRF `state`, 계정 통합 승인 상태를 서버에서 일관되게 관리한다 | 모바일 앱 또는 외부 API 토큰 발급이 핵심 요구가 될 때 |
| ORM | ORM 사용 긍정, Drizzle/Prisma/Kysely 비교 | 데이터관리 기준의 `_uuid`, 공통코드, 공통 메타 7종, 실제 DB 제약이 ORM 스키마에 반영되어야 한다 | 하네스 DB 기본값 확인 후 |
| 비동기 | 계정 통합 핵심은 동기 트랜잭션, 후속 작업은 DB Job Table 우선 | 트랜잭션 안에서는 핵심 데이터 이전만 처리하고 알림/재색인/대량 이전은 분리한다 | PDF 처리 MVP 시작 시 MQ 재검토 |
| E2E | Playwright 최소 도입 | 모든 케이스를 E2E로 만들지 않고 핵심 사용자 여정만 스모크 테스트로 유지한다 | PDF 뷰어와 주석 상호작용 구현 시 |

MVP 단계에서는 단순한 구성을 허용하되 전환 비용을 낮추는 경계가 더 중요하다. 따라서 프레임워크, ORM, 큐 제품은 바뀔 수 있다고 보고, 도메인 모델과 유스케이스, 포트 인터페이스를 먼저 안정화한다.
