# 00. 기술스택 심층 비교 및 개선 방향

## 1. 개요

본 문서는 PDFowers 프로젝트에 채택된 핵심 기술 스택(**언어, 프레임워크, ORM, 테스트 도구**)의 선정 배경과 장단점을 분석하고, 대안 기술군과의 비교 및 향후 아키텍처 개선 방향을 제시한다.

---

## 2. 계층별 기술 스택 심층 비교

### 2.1 언어 및 런타임: TypeScript & Node.js (22.x LTS)

| 비교 항목 | TypeScript + Node.js (채택) | Java (Spring Boot) | Python (FastAPI) | Go (Golang) |
| :--- | :--- | :--- | :--- | :--- |
| **특징** | JavaScript 상위 집합, 강력한 정적 타입 추론, 광범위한 풀스택 생태계 | 강력한 엔터프라이즈 생태계, 표준화된 DDD/OOP 지원 | AI/ML 생태계 최강, 빠른 프로토타이핑 | 초경량 바이너리, 압도적 동시성 및 메모리 효율 |
| **장점** | • 프론트/백엔드 간 DTO 및 스키마 완벽 공유<br>• 비동기 I/O 기반의 빠른 이벤트 루프<br>• AI 에이전트(Codex/Gemini)의 높은 코드 생성 품질 | • 엄격한 타입 및 성숙한 프레임워크 | • 풍부한 데이터/AI 라이브러리 연동 | • 매우 낮은 메모리 사용량 및 빠른 시작 속도 |
| **단점** | • 빌드/트랜스파일 단계 필요<br>• 싱글 스레드 기반 CPU 집약 작업 한계 | • 상대적으로 무겁고 보일러플레이트가 많음 | • 런타임 타입 검증 오버헤드, GIL 한계 | • 객체지향 상속 및 제네릭 표현의 제약 |
| **선정 이유** | PDFowers의 PDF 처리, 웹 뷰어(React/Vite), AI 에이전트 하네스 간의 **타입 공유 생산성 극대화** |

---

### 2.2 웹 프레임워크: Express.js

| 비교 항목 | Express.js (채택) | Fastify | NestJS |
| :--- | :--- | :--- | :--- |
| **특징** | Node.js 진영의 사실상 표준(De-facto standard) 미들웨어 프레임워크 | 고성능 JSON 직렬화 기반 차세대 경량 프레임워크 | Angular 스타일의 엔터프라이즈 모듈형 풀 아키텍처 프레임워크 |
| **장점** | • 극도의 단순성, 거대한 미들웨어 생태계<br>• 헥사고날/클린 아키텍처 도입 시 프레임워크 종속성 최소화 | • Express 대비 2~3배 빠른 초고속 라우팅<br>• 스키마 기반 자동 검증 | • DI(의존성 주입) 및 아키텍처 표준화 기본 제공 |
| **단점** | • 구조적 가이드라인이 없어 아키텍처 규격이 필요함 | • Express 미들웨어 호환 시 일부 어댑터 필요 | • 학습 곡선이 높고 프레임워크 결합도가 높음 |
| **향후 개선** | 현재는 헥사고날 어댑터로 Express를 사용하되, 대규모 트래픽 발생 시 **Fastify 또는 tRPC 라우터로 무중단 전환** 가능하도록 포트 설계 유지 |

---

### 2.3 데이터베이스 및 ORM: PostgreSQL & Drizzle ORM

| 비교 항목 | Drizzle ORM (채택) | Prisma | TypeORM |
| :--- | :--- | :--- | :--- |
| **특징** | "If you know SQL, you know Drizzle" 지향의 초경량 TypeScript ORM | 전용 스키마 언어(Schema DSL)와 Rust 기반 쿼리 엔진 | JPA/Hibernate 스타일의 데코레이터 기반 전통적 Active Record ORM |
| **장점** | • **Zero Overhead**: 번들 크기 극소, SQL과 1:1 매핑<br>• **완벽한 타입 추론**: 별도 코드 생성(Generate) 없이 TS 즉시 반영<br>• **JSONB 완벽 지원**: 문서 DB 구조(`doc_payload`) 완벽 타이핑 | • 직관적인 클라이언트 API<br>• 강력한 마이그레이션 도구 | • 익숙한 클래스 기반 데코레이터 모델 |
| **단점** | • 복잡한 다대다 릴레이션 시 수동 JOIN 작성 필요 | • Rust 엔진 바이너리 오버헤드 (Serverless 환경 콜드스타트) | • 타입 추론 한계 및 유지보수 정체 |
| **선정 이유** | PDFowers의 **관계형 메타 + 유연한 JSON Document 하이브리드 저장소** 요구사항에 가장 부합 |

---

### 2.4 테스트 프레임워크: Vitest

| 비교 항목 | Vitest (채택) | Jest | Node.js Native Test Runner |
| :--- | :--- | :--- | :--- |
| **장점** | • **ESM 네이티브 지원** (Babel/ts-jest 설정 불필요)<br>• **압도적인 속도** (Vite의 HMR/Worker 풀 활용)<br>• Jest 호환 API (`describe`, `it`, `expect`) | • 가장 널리 쓰이는 표준 | • 외부 의존성 0 |
| **단점** | • Vite 생태계에 최적화 | • ESM/TypeScript 설정 복잡, 느린 실행 속도 | • Mocking 및 Matcher 기능이 다소 빈약함 |

## 3. 향후 아키텍처 발전 로드맵

1. **단기 (Current)**:
   - 헥사고날(Ports & Adapters) 기반 단일 Node.js 서비스 구축
   - Drizzle ORM + PostgreSQL JSONB를 통한 세션/태스크/문서 관리
2. **중기 (Evolution)**:
   - **tRPC / OpenAPI 자동화**: 프론트엔드-백엔드 간 End-to-End Type Safety 강화
   - **이벤트 기반 아키텍처 (EDA)**: 세션/태스크 이벤트(상태 전이, Reconcile)를 도메인 이벤트로 발행하여 분리
3. **장기 (Scale)**:
   - AI 에이전트 서비스와 PDF 프로세싱 엔진(Worker)의 컨테이너/서버리스 분리
