# 20260609 MVP1 보완점 및 하네스 개발 준비

## 1. 목적

1차 MVP 개발 착수 전 보완이 필요한 항목을 정리하고, 다음 세션에서 하네스 엔지니어링 개발을 바로 진행할 수 있도록 사전 작업, 결정 필요사항, 구체화 제안 방향을 분리한다.

본 문서는 [요구사항 명세서](../00_산출물/01_프로젝트산출물/01_요구사항명세서.md), [프로덕트 요구사항](../02_기획관리/01_프로덕트요구사항.md), [도메인 설계](../03_설계관리/03_도메인설계.md), [인증 구현 가이드](../04_기술관리/03_인증구현가이드.md), [기획/설계/정책 구체화 필요 대상](./20260608_기획설계정책_구체화필요대상.md)을 기준으로 한다.

## 5.1 선택지별 장단점

### 이메일 인증 정책

| 선택지 | 장점 | 단점 | 검토 의견 |
| :--- | :--- | :--- | :--- |
| 필수 | 계정 회복, 알림, 보안 기준이 명확함 | 가입 마찰이 증가함 | 운영 기본값 후보 |
| 선택 | 가입이 빠르고 개발/테스트가 쉬움 | 미인증 계정의 알림/복구/권한 정책이 복잡해짐 | 로컬 개발 또는 초기 테스트 후보 |
| 환경별 설정 | 운영 보안과 개발 편의 균형 | 설정별 테스트 케이스가 늘어남 | 1차 제안 |

### 인증 기술 방식

| 선택지 | 장점 | 단점 | 검토 의견 |
| :--- | :--- | :--- | :--- |
| 서버 세션 + 직접 OAuth | 특정 인증 프레임워크 종속이 낮고 OAuth `state`, 계정 통합 승인 흐름에 적합 | 제공자별 OAuth 구현을 직접 관리해야 함 | 1차 제안 |
| Passport.js + 서버 세션 | OAuth 전략 생태계가 있고 Express와 친숙함 | 전략 품질 편차와 라이브러리 결합 존재 | Express 채택 시 검토 |
| JWT | 외부 API와 모바일 확장에 유리 | 토큰 폐기, 통합 직후 권한 반영, 보안 운영이 복잡 | MVP1 기본안으로는 낮은 우선순위 |
| 인증 전문 라이브러리 | 이메일/OAuth/세션 구현 속도가 빠름 | 라이브러리 데이터 모델에 계정 통합 정책을 맞춰야 할 수 있음 | 하네스/프레임워크 호환 확인 후 검토 |

### API 방식

| 선택지 | 장점 | 단점 | 검토 의견 |
| :--- | :--- | :--- | :--- |
| REST + OpenAPI | 범용성, 문서화, 외부 연동, 테스트 도구가 좋음 | 타입 공유는 별도 생성 도구가 필요 | 1차 제안 |
| tRPC | TypeScript 풀스택 타입 공유와 개발 속도가 좋음 | 외부 클라이언트와 공개 API 문서화가 약함 | 내부 앱 전용이면 유력한 2순위 |
| GraphQL | 조회 조합 유연성이 큼 | 인증/계정 통합 같은 명령형 흐름에는 과함 | MVP1 비권장 |
| 서버 액션/내장 RPC | 화면과 서버 구현 거리가 짧음 | 프레임워크 종속이 강하고 API 경계가 흐려질 수 있음 | 핵심 인증 API에는 신중 |

### ORM 방식

| 선택지 | 장점 | 단점 | 검토 의견 |
| :--- | :--- | :--- | :--- |
| Drizzle ORM | SQL 친화, 타입 안정성, 마이그레이션 제어가 좋음 | 고수준 관계 API는 Prisma보다 덜 풍부함 | PostgreSQL 중심이면 유력 |
| Prisma | 생산성과 스키마 가독성이 좋음 | 복잡 SQL과 세밀한 마이그레이션 제어가 부담일 수 있음 | 빠른 CRUD 중심 후보 |
| Kysely | 타입 안정 SQL 빌더로 제어력이 큼 | 마이그레이션/스키마 관리는 별도 조합 필요 | SQL 제어 중시 시 후보 |
| TypeORM | 데코레이터 기반 객체 모델이 익숙함 | 마이그레이션 예측성과 복잡 동작이 약할 수 있음 | 낮은 우선순위 |

### 비동기 처리

| 선택지 | 장점 | 단점 | 검토 의견 |
| :--- | :--- | :--- | :--- |
| 동기 트랜잭션 | 일관성이 명확하고 구현이 단순함 | 대량 데이터 이전이나 알림이 길어지면 응답 지연 | 계정 통합 핵심 처리 |
| DB Job Table | 별도 인프라 없이 재시도와 상태 추적 가능 | 고성능 메시징 기능은 제한적 | MVP1 후속 알림/작업 1순위 |
| RabbitMQ | 신뢰성 있는 메시징과 확장성이 좋음 | 운영 인프라와 모니터링 부담 | PDF 처리 단계부터 재검토 |

### Playwright

| 선택지 | 장점 | 단점 | 검토 의견 |
| :--- | :--- | :--- | :--- |
| MVP1 즉시 도입 | 로그인 화면 실제 동작을 빨리 검증 | UI 변경에 따른 유지보수 비용 발생 | 핵심 3~5개 시나리오만 도입 |
| 2차 MVP부터 도입 | 초기 개발 속도가 빠름 | 인증 회귀를 수동 확인해야 함 | 인증 UI가 단순하면 가능 |
| 통합 테스트만 유지 | 빠르고 안정적 | 브라우저 쿠키/리다이렉트 문제를 놓칠 수 있음 | 단독으로는 부족 |

### 리뷰 반영 후 잠정 선택

| 영역 | 잠정 선택 | 적용 시 유의사항 | 재검토 시점 |
| :--- | :--- | :--- | :--- |
| API | REST + OpenAPI 우선 | 입력 검증 스키마와 OpenAPI 문서가 어긋나지 않게 관리한다. | 외부 API 공개 범위가 확정될 때 |
| 서버 프레임워크 | MVP 초기에는 단순 HTTP 서버 또는 Express.js 허용 | 라우터는 도메인 유스케이스 호출만 담당하고 업무 규칙은 `domains/*/usecase`에 둔다. | API 규모가 커지고 모듈/DI/성능 요구가 명확해질 때 |
| 인증 | 서버 세션 + 직접 OAuth 우선 | OAuth `state`, 세션 저장소, 계정 통합 승인 상태를 서버에서 일관되게 관리한다. | 모바일 앱 또는 외부 API 토큰 발급이 핵심 요구가 될 때 |

## 6. 구체화 제안 방향

### 6.1 가입/로그인 흐름

MVP1에서는 화면과 API를 다음 흐름으로 단순화한다.

1. ID/PW는 기본 로그인 정보이며 사용자가 임의 삭제할 수 없다. 계정 삭제는 탈퇴 절차로 처리한다.
2. ID/이메일 회원가입은 `login_id`, `email`, `password`, `display_name`, `email_notification_opt_in`을 입력받는다.
3. 이메일 인증 필수 설정이 켜져 있으면 인증 완료 전 로그인 또는 주요 기능 접근을 제한한다.
4. 간편로그인 회원가입은 제공자 인증을 먼저 완료한 뒤, 서비스 `login_id`와 `password`를 추가 입력받는다.
5. 간편로그인은 제공자 인증 결과를 신뢰하므로 PDFowers 이메일 인증은 생략한다.
6. 이미 연결된 `(provider, provider_user_id)`가 있으면 신규 가입 대신 기존 로그인으로 안내한다.
7. 다른 계정에 연결된 간편로그인을 로그인 상태에서 연결하려 하면 `ACCOUNT_MERGE_REQUIRED`로 계정 통합 흐름에 진입한다.
8. 카카오, 네이버, 구글 간편로그인은 모두 해제 가능하다.
9. 이메일 인증 필수 설정에서는 인증 완료 이메일 삭제를 차단하고, 이메일 변경은 새 이메일 인증 완료 후 반영한다.

### 6.2 계정 통합 흐름

MVP1에서는 계정 통합을 완전 자동 병합이 아니라 승인 기반 작업으로 둔다.

1. 요청 계정이 다른 계정의 간편로그인 연결을 시도한다.
2. 서버는 `AccountMergeRequest`를 생성하고 요청/대상 계정, 제공자, 만료 시각, 상태를 저장한다.
3. 대상 계정으로 로그인한 사용자가 통합 범위와 되돌리기 어려운 항목을 확인한다.
4. 대상 계정 사용자가 승인하면 서버 트랜잭션으로 AuthIdentity를 대표 계정으로 이전한다.
5. 보조 계정은 `merged` 상태로 두고 감사 로그를 남긴다.

대표 계정은 MVP1에서 요청 계정 고정을 제안한다. 사용자 선택 방식은 UX와 충돌 처리가 커서 문서/주석/공유 데이터가 생기는 2차 MVP 이후 재검토하는 편이 안전하다.

### 6.3 데이터관리 기준 기반 DB 모델 초안

다음 세션 전 최소 모델은 [데이터관리 설계기준](../03_설계관리/데이터관리/00_데이터관리설계기준.md)에 맞춰 아래 범위로 잡는다.

| 모델 | 필수 속성 |
| :--- | :--- |
| `user_account` | `user_uuid`, `display_name`, `primary_email`, `user_status_cd`, `merged_into_user_uuid`, 공통 메타 7종 |
| `local_credential` | `user_uuid`, `login_id`, `password_hash`, `password_hash_alg_cd`, 공통 메타 7종 |
| `verified_email` | `verified_email_uuid`, `user_uuid`, `email`, `email_verified_at`, `email_notification_opt_in`, 공통 메타 7종 |
| `auth_identity` | `auth_identity_uuid`, `user_uuid`, `provider_cd`, `provider_user_id`, `email_from_provider`, `connected_at`, `last_login_at`, 공통 메타 7종 |
| `account_merge_request` | `merge_request_uuid`, `request_user_uuid`, `target_user_uuid`, `provider_cd`, `provider_user_id`, `merge_status_cd`, `expires_at`, `approved_at`, 공통 메타 7종 |
| `audit_log` | `audit_log_uuid`, `actor_user_uuid`, `audit_event_type_cd`, `target_type_cd`, `target_uuid`, `metadata_json`, `created_at` |

유니크 제약 후보는 `local_credential.login_id`, `verified_email.email`, `auth_identity(provider_cd, provider_user_id)`이다. 상태/유형은 공통코드, 물리 타입과 길이는 도메인사전으로 통제한다.

### 6.3.1 암호화 및 해시 기준

비밀번호는 암호화가 아니라 단방향 해시로 저장한다. OWASP Password Storage Cheat Sheet 기준에 따라 Argon2id를 1순위로 검토한다. Node.js/하네스 환경에서 Argon2id 운영이 어렵거나 배포 환경 제약이 있으면 bcrypt를 2순위로 검토한다. OAuth 토큰은 MVP1에서 저장하지 않는 방향을 우선 검토하고, 장기 API 호출이 필요해 저장해야 하는 경우에는 암호화 저장과 키 회전 정책을 별도 문서로 분리한다.
