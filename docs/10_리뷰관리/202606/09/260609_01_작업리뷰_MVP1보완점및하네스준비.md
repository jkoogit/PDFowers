## 3. 주요 결정 및 반영 기준

| 영역 | 반영 기준 |
| :--- | :--- |
| 내부 회원 식별자 | `user_uuid`를 사용하고, UUID 타입 컬럼은 `_uuid` 접미사로 통일 |
| 사용자 입력 ID | 사용자가 입력하는 로그인 ID는 `login_id`로 별도 관리 |
| 공통 메타 | `created_sys`, `created_at`, `created_by`, `updated_sys`, `updated_at`, `updated_by`, `version` 기준 |
| 날짜/일시 표현 | `dt`는 `yyyymmdd`, `dtm`은 `yyyymmdd hhmmss` 표현 기준 |
| API | REST + OpenAPI 우선, tRPC는 내부 앱 전용 보조 후보 |
| 서버 프레임워크 | MVP 초기에는 단순 HTTP 서버 또는 Express.js 허용, 전체 시스템은 Fastify/NestJS 전환 가능성 유지 |
| 인증 | 서버 세션 + 직접 OAuth 클라이언트 우선, Passport.js/JWT/인증 라이브러리는 비교 후보 |
| ORM | ORM 사용은 긍정, Drizzle/Prisma/Kysely를 데이터관리 기준 반영 가능성으로 비교 |
| 비동기 처리 | MVP1은 핵심 통합 트랜잭션 + DB Job Table 우선, PDF 처리 단계부터 RabbitMQ 등 MQ 재검토 |
| E2E | Playwright는 MVP1 핵심 로그인 여정 3~5개만 최소 도입 |
